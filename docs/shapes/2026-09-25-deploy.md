# Shape: деплой на VPS

## Цель

На чистом Ubuntu 24.04 бот поднимается тремя командами (clone, `.env`, `up -d --build`), работает неделю с `DRY_RUN=1` без присмотра, каждый рестарт виден в служебном боте, CI проверяет каждый push и PR.

## Подход

Один образ `app` (python:3.12-slim + uv, зависимости из `uv.lock` без dev), entrypoint применяет миграции и запускает `python -m digest`. Отдельный compose-проект `crm-digest-bot-prod`: `app`, `postgres:16`, `backup` на том же образе postgres с shell-скриптом из репозитория. Версия приходит build-аргументом `GIT_SHA` → `APP_VERSION` в образе → `Settings.app_version` → стартовое сообщение. CI: GitHub Actions, uv, ruff, mypy, pytest с testcontainers.

## Файлы

- `Dockerfile`: `COPY --from=ghcr.io/astral-sh/uv:<pin>`; слой зависимостей `uv sync --frozen --no-dev --no-install-project` по `pyproject.toml` + `uv.lock`, затем код и `uv sync --frozen --no-dev`. Установка проекта editable (по умолчанию uv): `CONFIG_DIR` и `TEMPLATES_DIR` считаются от `__file__` и ждут `/app/src`, `/app/config`, `/app/templates`. Пользователь `app` uid 10001. `ARG GIT_SHA=unknown`, `ENV APP_VERSION=$GIT_SHA`. Шаг сборки `python -c "ZoneInfo('Europe/Bucharest')"`: в python:3.12-slim tzdata сейчас есть (проверено), пакет `tzdata` в lock только для win32, смена базы не должна пройти молча.
- `.dockerignore`: `.git`, `.env*` (кроме `.env.example`), `backups/`, `docs/`, `tests/`, `.venv`, кэши. `docs/reference/` с данными клиентов в образ не попадает по построению.
- `deploy/entrypoint.sh`: `set -eu; alembic upgrade head; exec python -m digest`.
- `deploy/backup.sh`: POSIX sh. `backup.sh once`: если нет `digest-<UTC-дата>.dump`, `pg_dump -Fc` во временный файл и `mv` (оборванный дамп не считается сегодняшним); затем удаление `digest-*.dump` старше 30 дней; чужие файлы не трогает. `backup.sh loop`: `once` раз в час. Подключение через `PGHOST/PGUSER/PGPASSWORD/PGDATABASE`.
- `docker-compose.prod.yml`: top-level `name: crm-digest-bot-prod`, чтобы smoke-тест на ноутбуке не делил проект и volume с локальным `docker-compose.yml` (оба файла в одной папке, имя проекта иначе совпадёт). `app`: build с `args: GIT_SHA: ${GIT_SHA:-unknown}`, `env_file: .env`, `environment: DATABASE_URL` собран из `POSTGRES_*` с хостом `postgres` (перекрывает localhost из `.env`, один источник пароля), `depends_on: postgres: service_healthy`, `restart: unless-stopped`. `postgres`: volume `postgres-data`, healthcheck как в dev, без `ports`. `backup`: `postgres:16`, `entrypoint: sh /backup.sh loop`, `./deploy/backup.sh:ro`, `./backups:/backups`, restart unless-stopped. У всех `logging: json-file, max-size 10m, max-file 5`.
- `src/digest/settings.py`: `app_version: str = "dev"` (env `APP_VERSION`).
- `src/digest/app.py`: `startup_announcement(app_version, dry_run) -> str` («Бот запущен, версия abc1234, DRY_RUN=1»); `run_app` после `scheduler.start()` шлёт его через `notify_ops`. Только сервисный режим, не `report`/`snapshot`.
- `.github/workflows/ci.yml`: push и pull_request, `permissions: contents: read`, `astral-sh/setup-uv`, `uv sync --frozen`, `ruff check`, `ruff format --check`, `mypy`, pre-commit-хук `todo-needs-issue`, `pytest -q`. Второй job `docker build .` без push. Секретов нет.
- `docs/deploy.md`: сервер (apt upgrade, docker из репозитория Docker, unattended-upgrades с автоперезагрузкой в 03:00, firewall Hetzner только 22 входящий), deploy key ed25519 только на чтение, клон в `/opt/crm-digest-bot`, `.env` по `.env.example` с `DRY_RUN=1` и паролем `openssl rand -hex 24` (hex не ломает URL), запуск `GIT_SHA=$(git rev-parse --short HEAD) docker compose -f docker-compose.prod.yml up -d --build`, проверка (`ps`, `logs app`, сообщение в служебном боте, файл в `backups/`), перенос базы: `pg_dump -Fc` из локального контейнера, `scp`, на сервере `up -d postgres` → `pg_restore --clean --if-exists --no-owner` → `up -d` (alembic догонит только новые миграции), обновление `git pull` + та же команда up, откат `git checkout <sha>` + up; откат через миграцию только `alembic downgrade` до checkout или восстановление из дампа.
- `README.md`: ссылка на `docs/deploy.md`. `docker-compose.yml`: комментарий про продовый compose. `.env.example`: пометка, что в проде `DATABASE_URL` задаёт compose. `STACK.md`: строка CI. `docs/PLAN.md`: итог.

## Схема / API

Схема БД не меняется. Новая переменная `APP_VERSION` ставится образом, в `.env` её нет.

## Тест-план

- Unit `tests/unit/test_app.py`: `test_startup_announcement_contains_version_and_dry_run_flag` (seam `startup_announcement`). Вызов в `run_app` проверяет smoke-тест: `run_app` блокирующий и сам создаёт ботов, тестовый шов ради одной строки не делаем.
- Integration `tests/integration/test_backup_script.py`: `sh deploy/backup.sh once` через subprocess, фейковый `pg_dump` первым в `PATH`, `BACKUP_DIR` во временной папке, mtime через `os.utime` (одинаково на macOS и Linux). Кейсы: `test_backup_creates_todays_dump`, `test_second_run_same_day_does_not_dump_again`, `test_dumps_older_than_30_days_are_deleted_and_newer_kept`, `test_foreign_files_are_not_deleted`, `test_failed_pg_dump_leaves_no_dump_and_exits_nonzero`. Идёт в том же pytest в CI.
- Smoke на ноутбуке вручную: сборка образа, `docker-compose.prod.yml up` с локальным `.env` и `DRY_RUN=1`, в логах миграции и `scheduler started`, сообщение с sha в служебном боте, дамп в `./backups`, `docker compose restart app` даёт второе сообщение.

## Альтернативы

- **Версия из `.git` в образе или `git` в рантайме.** Отвергнуто: `.git` раздувает образ и тащит историю, в slim нет git. Build-arg проще; если забыть `GIT_SHA`, в сообщении будет `unknown`, это видно.
- **Бэкап cron-ом хоста или из `app`.** Cron хоста живёт вне репозитория и не воспроизводится тремя командами; `pg_dump` в `app` тянет клиент Postgres в образ и связывает бэкап с жизнью бота. Сторонние образы (ofelia и т.п.) исключены условием.
- **Расписание бэкапа точным временем (sleep до 03:00).** Отвергнуто: ежечасная проверка «есть ли дамп за сегодня» переживает рестарты без арифметики времени и таймзон в контейнере.
- **`${GIT_SHA:?}` вместо дефолта.** Отвергнуто: compose интерполирует файл при любой команде, `logs` и `ps` падали бы без переменной.

## Открытые вопросы

1. Сбой бэкапа виден только в `docker logs backup`. Предлагаю принять на неделю DRY_RUN и в harden добавить проверку свежести последнего дампа со стороны `app` (алерт в служебный бот). Или сразу?
2. Бэкапы лежат на том же диске, что и база. Включить Hetzner Backups (+20 % цены, 7 образов) в `docs/deploy.md` как обязательный шаг, или копирование на ноутбук вручную?
3. Job `docker build` в CI я добавил сверх задачи: без него сломанный Dockerfile всплывёт только на сервере. Оставить?
4. Сбой миграции при старте даёт цикл рестартов без стартового сообщения; сигнал только отсутствие сообщения. Для v1 считаю достаточным.

## Ответы на открытые вопросы (25.09.2026)

1. Проверка свежести дампа сразу, не в harden: `app` монтирует `./backups` только на чтение, после ежедневного отчёта проверяет, что самый свежий `digest-*.dump` моложе 26 часов, иначе алерт в служебный бот. Тест на функцию проверки.
2. Hetzner Backups обязательный шаг в `docs/deploy.md` (включён при заказе). Копирование на ноутбук не нужно.
3. Job `docker build` в CI остаётся.
4. Для v1 достаточно; в разделе «Проверка» `docs/deploy.md` явно: стартовое сообщение в течение двух минут после `up`, иначе `docker compose logs app`.

## Отступления при craft

- Проверка свежести: `src/digest/backup_check.py`, `stale_backup_alert(backup_dir, now) -> str | None`, вызывается в `report_job` после отчёта уровня `daily`. Каталог приходит из `Settings.backup_dir` (env `BACKUP_DIR`, задаёт только `docker-compose.prod.yml`; вне прода `None`, проверки нет). Порог `BACKUP_MAX_AGE = 26 ч` константой рядом с функцией: это эксплуатационный порог, привязанный к ритму `deploy/backup.sh`, а не бизнес-порог из `config/`. Если ежедневное расписание выключено в `schedules`, проверка тоже не идёт.
- Незавершённый дамп называется `digest-<дата>.dump.partial`: под `digest-*.dump` не подходит ни для ротации, ни для проверки свежести.
- Комментарий в `docker-compose.yml` ушёл в первый коммит (вместе с продовым compose), а не в документационный.
- Тесты скрипта бэкапа лежат в `tests/integration/`, хотя Postgres не поднимают: они запускают внешний процесс.
- CI на `ubuntu-24.04`, `astral-sh/setup-uv` закреплён по sha (v10.1.0), uv 0.12.5 как в `Dockerfile`; хук `todo-needs-issue` запускается через pre-commit.

## Дополнение после critique (25.09.2026)

Critique коммитов 291de2e..7cae66c: 5 block, 12 nice-to-have, 8 nit, все приняты. Решения:

1. **Сервер.** Hetzner CPX12 (линейка CX недоступна), Ubuntu 24.04, Nuremberg, SSH-ключ при заказе, Backups включены, облачный firewall только TCP 22. Заказ описан в `docs/deploy.md` по шагам консоли. ADR-001 не правим, пометка в STACK.md.
2. **Раздел «0. Что нужно заранее».** Источник каждой переменной `.env`: BotFather для токенов, `/setprivacy` → Disable для основного бота (с переподключением к группе), chat_id через `getUpdates`. `TELEGRAM_GROUP_CHAT_ID` на неделю DRY_RUN заглушка `-1`: валидатор требует три разных chat_id, настоящий id вписывается только при переходе на прод.
3. **`COMPOSE_FILE=docker-compose.prod.yml` в серверном `.env`.** Из инструкции `-f` убран; текст алерта `docker compose logs backup` становится верным на сервере. В `.env.example` строка закомментирована: локально она переключила бы `docker compose` на продовый файл.
4. **`init: true` у app, postgres, backup.** PID 1 без обработчика SIGTERM (python после `exec`, `sh` в backup) давал 10 с ожидания и SIGKILL на каждый stop.
5. **`./deploy:/deploy:ro` вместо одного файла.** Bind-mount файла держит inode, после `git pull` backup выполнял бы старый скрипт даже после restart. После смены скрипта нужен `docker compose restart backup` (раздел 8 инструкции).
6. **Проверка свежести сообщает о своём сбое.** Исключение `stale_backup_alert` ловится в `report_job` так же, как `run_report`: лог `backup check failed` и «Проверка бэкапа упала: <describe_error>.» в служебный бот. Тесты на проводку: daily шлёт алерт, weekly не проверяет, битая ссылка `digest-*.dump` даёт алерт о сбое проверки (реальное исключение без моков своих модулей).
7. **Перенос базы только после первого `up`** (папку `backups/` создаёт compose). `stop app backup`, `up -d --wait postgres`, `pg_restore --clean --if-exists --no-owner --single-transaction --exit-on-error`, сверка `count(*)` из `snapshot_runs` и `lead_snapshots` с ноутбуком, затем явный шаг «на ноутбуке больше ничего не запускать».
8. **Обновление нумерованными шагами:** запомнить `OLD_SHA` → `git pull` → `alembic current` (записать ревизию) и новые файлы `alembic/versions` через `git diff` → дамп `before-<OLD_SHA>.dump` всегда → `up`. Отступление: вместо `alembic history` в работающем `app` новые миграции смотрим через git, потому что контейнер до `up` содержит старый код и показывает старую историю.
9. **Откат** с примером `alembic downgrade 0001` и способом найти ревизию старой версии через `git show <sha>:alembic/versions`; путь через восстановление дампа с теми же флагами `pg_restore`.
10. **Раздел «Переход на прод через неделю»:** `DRY_RUN=0`, настоящий `TELEGRAM_GROUP_CHAT_ID`, `up -d --force-recreate app`, стартовое сообщение с `DRY_RUN=0`. Помечен необратимым по CLAUDE.md, только после подтверждения владельца проекта.
11. **Проверка перезагрузкой** в разделе 4: `reboot`, `ps`, второе стартовое сообщение; `systemctl is-enabled docker` при установке.
12. **CI:** push только на `main` (pull_request на все ветки), `actions/checkout` по sha (v5.1.0), после сборки образа `python -c "import digest.app"` в контейнере. Импорт `digest.app`, а не `digest`: пакетный `__init__` пуст и ничего не проверяет, `digest.app` тянет весь сервисный код.
13. **Базовый образ `python:3.12.14-slim`.** uv уже закреплён тегом 0.12.5.
14. **`.partial` в ротации** по тому же порогу; формулировка «удаляются дампы старше 30 полных суток» (`find -mtime +30`) в скрипте и инструкции.
15. **Мелочи инструкции:** отпечаток host key GitHub при первом clone, выключение входа по паролю через `sshd_config.d/10-no-password.conf`, `apt install git`, команды рассчитаны на `POSTGRES_USER=digest`.
