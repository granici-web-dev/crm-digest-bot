# Shape: ежедневные модули d2–d6 и долги первого живого прогона

Статус: согласован 25.09.2026, ответы на открытые вопросы в конце.

## Цель

Ежедневное сообщение после блока d1 содержит пять блоков d2–d6 (RO/RU). Каждая цифра считается функцией в `metrics/`, модуль только рендерит. Алерт «модули включены, но не реализованы» для daily исчезает. Заодно закрываются пять долгов первого прогона.

## Подход

Новый файл `src/digest/metrics/daily_checks.py`: пять чистых функций над кадром лидов, каждая возвращает frozen dataclass. Повторно используем уже проверенное, а не пишем заново:
- окна: `daily_window` (d2, d5, d6);
- «лид» и группа web: `lead_row_flags` из `metrics/daily.py` (d5 и d6 считают лиды ровно так же, как строки Leads в d1);
- висящая оферта: `lead_counts_by_showroom(...).active_offers_14` из `metrics/kpi.py` с периодом «всё время до конца окна» (d4 = та же формула, что ACR);
- просроченные revenire: `overdue_revenire` из `metrics/extra.py` (d3);
- правило «снапшот ровно за вчера» как в d1 (d4).

Модули: `src/digest/reports/modules/daily_checks.py`, пять функций по образцу `seller_format_report`, регистрация в `IMPLEMENTED_MODULES`. Шаблоны `templates/<name>.{ro,ru}.j2` на каждый модуль. Блок без находок печатает одну строку с «nu» / «нет».

## Правила модулей

**Общее: «не взят».** Лид с `assigned_to.id` консультанта с `not_taken: true` (id 7, Marketing Sofa) или без `assigned_to` идёт в отдельную группу «Nepreluate / Не взяты», первой строкой блока. Имена консультантов выводятся как в `managers.yaml`, целиком (`Raileanu  Leon` с двумя пробелами как в mefi, без обрезки до фамилии).

**d2 untouched_leads.** Кандидаты: `created_at ≥ window.end − lookback_days` и `created_at < window.end`, не PARTNERSHIP, не источник `sources.showroom_visit` (визит в шоуруме это касание). Без касания: `status_changed_at` null ∧ `last_contact_at == created_at` ∧ `is_ofertat` false ∧ лид создан не консультантом (`created_by.id` не из консультантов с `active: true`; лид, созданный продавцом руками, уже обработан). `created_by_id` берётся из raw при загрузке кадра. Лид «не взят» попадает в d2 независимо от правила касания. Возраст = `window.end − created_at` (не `now()`: повтор отчёта даёт те же цифры), в выдачу только возраст > `threshold_hours`. По группе: число лидов и самый старый возраст в часах. `params: { threshold_hours: 4, lookback_days: 3 }`.

**d3 overdue_revenire.** Строка `Godja 4 (cea mai veche: 6 zile)`. В `overdue_revenire` условие `data_revenire ≤ today` меняется на `< today` (строго). Новая функция группирует результат по консультанту: число лидов и максимальная просрочка в днях (`today − data_revenire`). Совпадение `Data revenire` с днём создания не отсекаем.

**d4 stale_offers.** `active_offers_14` по шоурумам на `report_date`, лиды без шоурума отдельной строкой. Дельта итога к вчера: та же функция на вчерашнем кадре с `analysis_date = report_date − 1`, только если `previous.snapshot_date == report_date − 1`, иначе «—». Срок только `kpi.yaml active_offer_stale_days`; в `modules.yaml` params у d4 уже нет.

**d5 anomalies.** Два правила, пороги в `modules.yaml` d5 params:
- `site_zero_min_average` (2): лидов с источником `Site` (не вся группа web, она остаётся для d1) в окне 0, а среднее по семи предыдущим суточным окнам (19:00→19:00, по `created_at` сегодняшнего кадра) ≥ порога. Выводим среднее с одним знаком.
- `irelevant_spike_min` (5): у консультанта лидов с причиной IRELEVANT, у которых `status_changed_at` (или `created_at`, если статус задан при создании) попадает в окно, ≥ порога.

**d6 same_weekday_compare.** Лиды: сумма пяти строк d1 (`lead_row_flags`) в окне сегодня и в окне `report_date − 7`, оба из сегодняшнего кадра. Контракты: `converted_at` в каждом из двух окон. Строка вида `Lead-uri azi: 11 (joia trecută: 8) · Contracte: 1 (0)`, день недели из словаря в шаблоне.

## Долги первого прогона

1. `config/status-mapping.yaml`: `"BIFE 2026"` в `sources.other`, `"FacebookMessanger"` в `sources.web` (написание как в mefi).
2. Алерт UNMAPPED: раннер делит `new_unmapped_lead_ids` по `status_name` из `lead_snapshots` этого снапшота (не из кадра: там нет лидов тестового аккаунта): «лиды без статуса (Necompletat), N, id…» и «неизвестный статус «X», N, id…, добавьте в status-mapping.yaml».
3. `alembic/env.py`: URL из `sqlalchemy.url` вызывающего или `os.environ["DATABASE_URL"]`; импорт `Settings` убирается (миграция не требует токенов ботов).
4. `alert_snapshot_findings` читает `custom_field_mismatches` и шлёт алерт по записям `unknown_raw_key`: ключи и число лидов, без значений.
5. `managers.yaml`: `not_taken: true` у id 7; `Manager.not_taken: bool = False`, валидатор: `not_taken` только при `active: false`.

## Отвергнутые варианты

- **Свой счётчик висящих оферт в d4.** Две копии формулы ACTIVE_OFFERS_14 разойдутся при первой правке; вызываем `lead_counts_by_showroom` с широким периодом.
- **d5 по старым снапшотам.** Среднее за 7 дней из сегодняшнего кадра по `created_at` не зависит от пропущенных снапшотов; исчезнувшие лиды (удалённые в mefi) немного занижают среднее, для порога аномалии это приемлемо.
- **Возраст d2 от `now()`.** Повтор отчёта в 19:40 дал бы другие цифры, чем в 19:30; берём конец окна.
- **Один общий шаблон на d2–d6.** Нарушает инвариант 5 (модуль = своя функция и свой шаблон), выключение модуля через `/settings` станет правкой шаблона.

## Ответы на открытые вопросы (25.09.2026)

1. `status_name` null не добавляем: `IN PROCES` статус по умолчанию у лидов из API. Касанием считается создание лида консультантом с `active: true` (`created_by.id`).
2. Лид на Marketing Sofa или без консультанта не взят независимо от касаний.
3. `Godja 4 (cea mai veche: 6 zile)`.
4. Только `Site`, параметр `site_zero_min_average`.
5. `site_zero_min_average: 2` (646 лидов с сайта за восемь месяцев, меньше трёх в день), `irelevant_spike_min: 5`.

Craft тремя коммитами: долги и конфиги; metrics + ADR-004 + kpi-definitions + unit-тесты; модули, шаблоны, рендер и интеграция.

## Дополнение после critique (25.09.2026)

Critique диапазона 5d51519..24b42a6 (две оси, стандарты и спека): все замечания приняты. Решения:

**Формулы**
1. `ACTIVE_OFFERS_14` = `is_ofertat` ∧ категория `ACTIVE` или `ACTIVE_FOLLOWUP` ∧ `analysis_date − date(last_contact_at) > active_offer_stale_days`. Причина: на живом снапшоте d4 показал 564 «висящие» оферты, почти все это потерянные лиды с офертой в истории; бриф и меню говорят «oferte active». ADR-005, `kpi-definitions`, эталон пересобирается `scripts/build_etalon.py` (меняются `active_offers_14` и `acr`). Закрывает пункт «LOST в висящих офертах».
2. d2, касание по контакту: `last_contact_at − created_at > 60 секунд`. Пустое или отрицательное значение = не касались. Замер на живом снапшоте: 982 лида с точным равенством, 14 со сдвигом до минуты, 82 без значения, 4 с контактом раньше создания. Запись в `kpi-definitions`.
3. d2, лид создан консультантом, но не назначен: остаётся в блоке как «не взят», заголовок блока «Lead-uri neatinse sau nepreluate» / «Лиды без касания или не взятые».
4. d2, `created_by_id` вне `managers.yaml`: `unknown_manager_ids` проверяет и `assigned_to_id`, и `created_by_id`, алерт общий.
5. Итог d2 и d3 и максимальный возраст по всем группам возвращает `metrics/`. Шаблон печатает общий максимум отдельной цифрой, у каждой группы её собственный максимум; `sum` в шаблонах нет.
6. Правило «снапшот ровно за вчера» одной функцией в `metrics/daily.py`, её вызывают d1 и d4.

**Поведение**
7. `unknown_raw_key`: алерт только по ключам, которых не было в предыдущем успешном снапшоте, как у UNMAPPED.
8. d4 при нуле висящих оферт показывает дельту к вчера.
9. d5: группа «не взят» первой, как в d2 и d3.
10. Пустой кадр: каждая проверка d2–d6 отдаёт пустой результат, без NaT в периоде d4.
11. Окно среднего d5 (7 дней) в params d5 (`site_average_days`), шаблон берёт число из результата.

**Стандарты**
12. `ManagerFinding.oldest` разделяется по единицам: часы в d2, дни в d3.
13. params модулей разбираются в типизированную модель один раз при загрузке и лежат на модуле; `metrics/` не валидирует повторно; поиск модуля по имени с понятной ошибкой; проверка params отдельным валидатором.
