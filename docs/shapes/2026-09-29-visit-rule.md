# Shape: единое определение визита (ADR-007)

Статус: **подтверждён** (см. «Согласовано»). Основание: ADR-006 (правило визита d1), «Vizita в d1 и визиты в w2, KPI, чате расходятся» в `docs/kpi-definitions.md`.

## Цель

Одно правило визита во всех расчётах: w2 «Vizite showroom» за неделю 39 совпадает с «din N» в w6 и с суммой Vizita d1 за семь дней. Директор больше не видит 28 против 27.

## Подход

Визит это свойство лида, а не отчётного периода. Revenire считается относительно начала **собственного ежедневного окна лида** (`daily_window` дня, чьё окно содержит `created_at`), а не начала периода отчёта. Для лида из окна d1 это ровно `period.start`, поэтому d1 не меняется. Неделя и месяц тогда по построению равны сумме дней d1.

Флаги считаются один раз при подготовке кадра (`prepare_lead_frame`) и лежат колонками. Все потребители читают колонки, никто не сравнивает `source_name` с `sources.showroom_visit` сам.

```python
# src/digest/metrics/visits.py
def showroom_visit_flags(lead_frame: pd.DataFrame, config: AppConfig) -> pd.DataFrame:
    # индекс lead_frame; колонки:
    #   is_showroom_source   источник из sources.showroom_visit (физический приход, любой)
    #   is_showroom_revenire source ∧ category ≠ PARTNERSHIP ∧ контакт совпал с лидом,
    #                        созданным раньше начала своего ежедневного окна
    #   is_showroom_visit    source ∧ category ≠ PARTNERSHIP ∧ ¬revenire
```

Совпадение контакта: равен непустой ключ телефона или e-mail (как в ADR-006). Вычисление векторное: по каждому ключу `min(created_at)` в снапшоте; revenire, если минимум по телефону или e-mail раньше начала своего окна. Лид без ключей (снапшоты до миграции 0005) revenire не бывает, он визит. «Не PARTNERSHIP» проверяется только по категории: `sources.partner` не пересекается с `sources.showroom_visit` (валидатор групп).

`is_showroom_visit` в `frame.py` исчезает как отдельное определение и становится колонкой из этой функции. `matches_contact_created_before` из `daily.py` уходит в `visits.py`. `daily_window_days` переезжает из `weekly.py` в `daily.py` (иначе `visits.py` импортирует `weekly.py` ради одной функции), отдельным коммитом `refactor:`.

## Отвергнутые варианты

- **Revenire от начала периода отчёта** (каждый потребитель зовёт функцию со своим `Period`). Лид с контактом, встречавшимся в понедельник, в среду был бы revenire в d1 и визитом в w2: неделя ≠ сумме дней, одна и та же запись меняет смысл в зависимости от отчёта. Хуже исходной проблемы.
- **Revenire = любой более ранний лид с тем же контактом, без окна.** Проще, но ломает d1: утренний WhatsApp и вечерний приход в шоурум дали бы revenire; ADR-006 выбрал границу окна именно из-за этого.
- **Фильтр только в w2, KPI не трогать.** Это текущее расхождение в другой форме: w2 и SC снова разойдутся при первом revenire.

## Риски

- **Правило почти не срабатывает.** ADR-006 исходит из слов владельца «повторный приход заводится новым лидом», но за семь месяцев из 988 Showroom-лидов revenire 0, телефон делят всего 34 лида из 3056. Вероятнее, mefi не даёт завести второй лид на тот же телефон, или продавцы ведут повторный приход на старом лиде (статусы Revenire 1–3). Тогда «Reveniri» всегда 0, а повторный визит в наших цифрах не виден вовсе. Вопрос 2 ниже.
- Чат по закрытым периодам до 28.09 читает снапшоты без ключей: там revenire невидим, визиты = Showroom без партнёров. На сегодня это те же числа.
- Удалённый в mefi ранний лид превращает revenire в визит задним числом (сравнение внутри снапшота). Принимаем, как в ADR-006.

## Открытые вопросы владельцу

1. **Revenire в числителе SC.** Предлагаю: revenire не входит ни в числитель, ни в знаменатель, но визит считается конвертированным, если `Clienți` стал он сам **или** более поздний лид с тем же контактом. Довод: SC меряет, сколько посетителей стали клиентами. Если клиент пришёл второй раз и договор оформили на новом лиде, при правиле «только сам лид визита» продажа потеряется, а если добавить revenire в числитель без знаменателя, числитель перестанет быть подмножеством знаменателя (SC может превысить 100 %). Атрибуция к первому визиту считает человека один раз и продажу один раз. Практически: на живых данных случаев 0, поэтому в этой фиче реализуем «только сам лид визита» (числитель ⊂ знаменатель), атрибуцию добавим отдельным ADR, когда появятся revenire или владелец скажет «да» сейчас.
2. **Как продавцы на самом деле заводят повторный приход?** Данные противоречат ADR-006 (выше, «Риски»). Если повторный приход ведётся на старом лиде, правило revenire по контакту стоит заменить (например, на статус Revenire N при приходе), и это отдельный shape.
3. Строка «Reveniri: N» при нуле: показывать всегда (предлагаю) или только при N > 0?

## Согласовано (29.09.2026)

1. Revenire не входит ни в числитель, ни в знаменатель SC; конверсия визита это только сам лид визита (числитель ⊂ знаменатель). Атрибуция продажи по контакту к первому визиту это отдельный ADR, когда появятся случаи revenire.
2. Факт по снапшоту 28.09: mefi дубли разрешает (4 лида `is_duplicate`), 34 лида делят телефон, пар Showroom–Showroom нет, `Data revenire` заполнена у 1441 лида. Вывод: повторный приход ведётся на старом лиде, revenire по контакту ожидаемо ≈ 0. Правило оставляем по ADR-006; метрика повторного визита по изменению существующего лида это отдельный shape после ответа владельца. Записано в ADR-007 и `docs/kpi-definitions.md`.
3. «Reveniri: N» в w2 показывается всегда, включая 0.
4. w1 и d2 переходят на `is_showroom_source`, смысл не меняется.

Статус: **подтверждён**.
