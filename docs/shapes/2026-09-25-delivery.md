# Shape: ядро доставки и модуль d1 (сессия 5)

Статус: согласован 25.09.2026, ответы на открытые вопросы в конце.

## Цель

В 19:30 по Бухаресту в группу уходит ежедневный отчёт с блоком d1 в формате продавцов; сбой снапшота или модуля не блокирует отправку, ошибки уходят в служебный бот, повторный запуск за тот же период ничего не шлёт.

## Подход

Один процесс: `python -m digest` поднимает `AsyncIOScheduler` (APScheduler 3, `Europe/Bucharest`) и ждёт в asyncio-цикле; aiogram `Bot` используется только для отправки, polling не стартует. Раннер отчёта это одна async-функция: период → снапшот → включённые модули → рендер Jinja2 → разбиение → отправка → `report_runs`. Модуль это пара «функция в `reports/modules/` + шаблон», счёт d1 живёт в `metrics/daily.py` (инвариант 1). Реестр реализаций это словарь `module_id → функция`, без классов и Protocol (одна реализация на модуль).

## Схема / API

Новых таблиц и миграций нет. `report_runs.status` ∈ {`running`, `success`, `partial`, `failed`}: `partial` = отправлено с пометками (снапшот или модуль недоступен). Строки `schedules`: daily `30 19 * * *`, weekly `0 9 * * mon`, monthly `0 9 1 * *`, yearly `0 9 5 1 *`. `settings`: `('report_language', '"ro"')`.

## Раннер: поведение

1. `chat_id` = test при `DRY_RUN=1` или `--dry-run`, иначе group. Ключ идемпотентности (tenant, level, period_start, chat_id): `INSERT … ON CONFLICT DO NOTHING`; есть `success`/`partial` → выход без отправки; есть `running` → выход и алерт (возможна половина отправки, решает человек); есть `failed` → строка переиспользуется, отчёт шлётся заново.
2. Daily: `load_lead_frame(today)`; `SnapshotMissingError` → все модули на источнике A заменяются одной пометкой, алерт «снапшот за дату отсутствует или failed».
3. Из `snapshot_runs` сегодняшнего success: `new_unmapped_lead_ids`, `won_converted_mismatch_ids` → алерты (только id и счётчики). `unknown_manager_ids(frame)` → алерт.
4. Каждый модуль в `try/except Exception`: блок заменяется пометкой, в ops `module_id` + `describe_error`. Модуль включён в конфиге, но нет в `IMPLEMENTED` → не рендерится, один алерт на прогон (не в группу).
5. Ни одного блока, кроме пометок «не реализовано» → ничего не шлём, `report_runs.status = failed`, `error = "no modules"`, алерт (это касается weekly/monthly/yearly до их shape).
6. Отправка: части по 4096, `message_ids` пишутся после каждой части; ошибка отправки → `failed`, алерт, уже отправленные id сохранены.

## d1: счёт (`metrics/daily.py`)

- Окно `[19:00 вчера, 19:00 сегодня)` по `created_at`, Bucharest (`kpi.Period`, полуоткрытое, как остальные метрики).
- Строки Leads, взаимоисключающие, по порядку: PARTNERSHIP (категория) → Designer/Colaboratori; источник Showroom ∧ ACTIVE_FOLLOWUP → Alte/Showroom (revenire); `sources.web` → Mail/FB/IG; `phone` → Telefon; `whatsapp` → WhatsApp. См. открытый вопрос 1 про остаток.
- Разница снапшотов (сегодня против success за вчера по `lead_id`, шоурум по сегодняшней строке):
  - Vizita = объединение по lead_id: новые лиды (нет вчера) с источником `showroom_visit` ∪ лиды со статусом `showroom_visit_status` сегодня и другим статусом (или отсутствием) вчера.
  - Oferta = `is_ofertat` сегодня ∧ не `is_ofertat` вчера (или новый).
  - Contract Cantitate = WON сегодня ∧ не WON вчера (или новый).
- Предыдущий снапшот берётся, только если его дата = сегодня − 1. Иначе (первый день, пропуск) три строки «—» и пометка: иначе разница покрыла бы несколько дней под подписью одного.
- Reoferta, Încasări: «—» и одна сноска на отчёт «sursa B indisponibilă».
- Шоурумы из `showrooms` конфига в его порядке; лиды без шоурума в итоге и в строке «Fără showroom: N» при N > 0. Заголовок `Sofabelle {showroom}` с именем как в mefi (`Brașov`, не `Brasov` из образца).

## Тест-план

- Snapshot (syrupy): рендер d1 RO и RU на фиксированных `SellerFormatCounts`, включая «—»-вариант и «Fără showroom».
- Integration (testcontainers + фейковая сессия aiogram) через `run_report`: второй запуск не шлёт; `failed` перезапускается; модуль, бросающий исключение, → остальные блоки ушли, пометка в группе, ошибка в ops; нет снапшота → отчёт с пометкой + алерт; `DRY_RUN` → вызовы только в test chat_id, продовый ни разу; `new_unmapped_lead_ids` → алерт без имени/телефона клиента.

## Альтернативы

- **Раннер как класс с зависимостями / Protocol модуля.** Отвергнуто: одна реализация, PRINCIPLES «Protocol при второй реализации». Зависимости передаются dataclass `ReportDeps`.
- **Идемпотентность через advisory lock вместо уникального ключа.** Ключ уже есть в `report_runs`; `ON CONFLICT` проще и переживает рестарт процесса. Lock нужен снапшоту, раннеру нет.
- **Разница снапшотов в SQL (self-join lead_snapshots).** Отвергнуто: метрика тогда вне `metrics/`, режим вопросов не сможет вызвать ту же функцию; два фрейма по ~несколько тысяч лидов в pandas дёшевы.
- **Diff с любым последним success.** Отвергнуто ради корректности: «Oferta: 5» за два дня под датой одного дня это неверная цифра.

## Ответы на открытые вопросы (25.09.2026)

1. `Colaborare` → Designer/Colaboratori; `sources.other` → Alte/Showroom (revenire) вместе с Showroom ∧ ACTIVE_FOLLOWUP. Лид с источником Showroom вне ACTIVE_FOLLOWUP это визит: идёт в Vizita и не входит в строки Leads. Итог «Leads N» это сумма пяти строк Leads, как у продавцов.
2. RU-шаблон d1: подписи строк румынские, переводятся шапка, пометки и сноска.
3. `running` старше 30 минут считается `failed`: раннер помечает его при следующем запуске, шлёт алерт «прогон прерван, отчёт отправлен заново» и отправляет отчёт целиком. Дубль в группе после краха лучше, чем отчёт, которого нет до ручного UPDATE. `running` моложе 30 минут: выход без отправки.

Critique коммитов 62cc137..aea65ea: 23 замечания и рекомендация к проверке DRY_RUN, все приняты. Harden четырьмя коммитами.
