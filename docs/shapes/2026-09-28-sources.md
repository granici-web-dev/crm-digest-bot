# Shape: m7 и w6, конверсия и нерелевантные по источникам и кампаниям (28.09.2026)

Статус: подтверждён 28.09.2026, решения в разделе «Согласовано».

## Цель

Месячный m7 показывает воронку и SCR/IRR по источникам mefi и по UTM_Campanie; недельный w6 показывает источники и кампании с наибольшей долей IRELEVANT и сравнивает с прошлой неделей. Оба модуля и будущий инструмент чата считают одной функцией разбивки.

## Факты (живой снапшот 28.09.2026, скрипт только со счётчиками)

- 3056 лидов, UTM_Campanie заполнено у 362 (11,8 %), 14 разных значений. Источники заполненных: Site 353, Mail 8, WhatsApp 1. Пустых строк и значений с пробелами по краям нет, коллизий по регистру нет.
- Размеры кампаний за всю историю: 316, 21, 7, 5, 4 и девять по 1. Кампаний с ≥ 5 лидами 4, с ≥ 10 две. IRELEVANT в них: 83 из 316, 7 из 21, 1 из 7, 1 из 5.
- Заполненных по месяцам created_at: апр 50, май 30, июн 96, июл 56, авг 89, сен 41. В месячной таблице кампаний будет 1–3 строки, в неделе обычно одна кампания выше порога.
- Лидов в месяц по источникам (июн–сен): Showroom 124–184, Site 81–152, WhatsApp 43–64, Telefon 37–58, Mail 2–66, BIFE 2026 42 (сен), остальные 0–7. В неделю в среднем: Showroom 33,6, Site 24,2, WhatsApp 11,6, Telefon 8,9, Mail 7,1, BIFE 3,0, прочие < 1.

## Подход

1. Новая колонка кадра `utm_campanie`: `load_lead_frame` читает её из `lead_snapshots.raw` (`jsonb_path_query_first` по `field_id` из `custom_fields.utm`, элемент с name `UTM_Campanie`), как сейчас читается `created_by_id`. Пустая строка и пробелы на границе → NULL. Миграции нет: raw уже содержит поле 39 (белый список `raw_custom_fields.keep`).
2. Одна функция разбивки в новом `metrics/breakdown.py` поверх `count_flags` и `kpis_from` из `kpi.py`: формулы не повторяются, строки в сумме дают `lead_counts` компании по построению.
3. m7 и w6 это тонкие функции в `metrics/monthly.py` и `metrics/weekly.py` на окнах, которые уже есть: `month_window` (как m2/m4) и `weekly_window` (как w3). Итог IRR в w6 равен IRR в w3, итог m7 равен воронке компании в m2.
4. Прошлая неделя w6 берётся из `context.week_ago` (снапшот прошлого воскресенья), не из текущего снапшота: IRELEVANT ставят с задержкой, и прошлая неделя по сегодняшнему снапшоту была бы «старше» текущей. Это же правило закрытых периодов у чата («saptamana_trecuta по снапшоту своего последнего дня»), цифры совпадут. Нет снапшота → столбец прошлой недели «—», как оферты в w8.

## Сигнатуры (`src/digest/metrics/`)

```python
# breakdown.py
BREAKDOWN_COLUMNS = ("source_name", "utm_campanie")   # enum и для инструмента чата

@dataclass(frozen=True)
class BreakdownRow:
    key: str | None          # значение как в mefi; None = пусто
    counts: LeadCounts
    kpis: Kpis

@dataclass(frozen=True)
class LeadBreakdown:
    rows: tuple[BreakdownRow, ...]        # ≥ min_leads, лиды по убыванию, при равенстве по имени
    other: BreakdownRow | None            # свёрнутые (< min_leads), key=None, counts суммой
    other_keys: tuple[str, ...]           # что свёрнуто, для «Alte surse (3)» и чата
    without_key: BreakdownRow | None      # пустое значение, никогда не сворачивается
    total: BreakdownRow                   # = lead_counts компании на том же окне

def lead_counts_by_column(lead_frame, column, period, analysis_date, config) -> dict[str | None, LeadCounts]
def lead_breakdown(lead_frame, column, period, analysis_date, config, min_leads: int) -> LeadBreakdown
def add_counts(counts: Iterable[LeadCounts]) -> LeadCounts   # в kpi.py, рядом с counts_from_sums

# monthly.py
@dataclass(frozen=True)
class MonthlySourceConversion:
    month: date
    by_source: LeadBreakdown
    by_campaign: LeadBreakdown          # without_key не выводится, total = только лиды с кампанией
    leads_with_campaign: int
    leads_total: int
    campaign_share: float | None        # ratio(leads_with_campaign, leads_total)

def monthly_source_conversion(lead_frame, report_date, config) -> MonthlySourceConversion

# weekly.py
@dataclass(frozen=True)
class IrrelevantRow:
    key: str
    leads: int
    irr_leads: int
    irr: float | None
    irr_previous: float | None          # None: нет week_ago или у ключа 0 лидов на прошлой неделе
    meets_target: bool | None           # цель irr из kpi.yaml targets, как в m5

@dataclass(frozen=True)
class WeeklyIrrelevant:
    by_campaign: tuple[IrrelevantRow, ...]
    by_source: tuple[IrrelevantRow, ...]
    total_irr: float | None             # = w3
    total_irr_previous: float | None

def weekly_irrelevant(lead_frame, week_ago: PreviousSnapshot | None, report_date, config) -> WeeklyIrrelevant
```

Ранжирование w6: только ключи с `leads ≥ min_*_leads` на текущей неделе, по IRR убыванию, затем по `irr_leads`, затем по имени; первые `top_rows`. Пустой источник и пустая кампания в рейтинг не входят (у них нет имени, по которому действовать), но входят в `total_irr`.

## Альтернативы (отвергнуты)

- **Колонка `utm_campanie` в `lead_snapshots` миграцией.** Быстрее запрос, но колонка на одно поле из четырёх и бэкфилл по старым снапшотам; raw уже хранит поле, путь чтения тот же, что у `created_by_id`.
- **Обобщить `lead_counts_by_showroom`/`by_manager` в одну функцию сейчас.** Правило трёх выполнено, но у шоурумов свой порядок из конфига и ключ None всегда. Это отдельный `refactor:` после фичи, при зелёном эталоне, не внутри.
- **Прошлая неделя w6 по текущему снапшоту** (как лиды и контракты в w8). Проще, работает без week_ago, но смещает сравнение: IRELEVANT проставляют через дни, прошлая неделя выглядела бы хуже текущей без реальной причины, и цифра разошлась бы с ответом чата.
- **Столбец «Vizite» в m7.** Визит = лид с источником из `sources.showroom_visit`, поэтому в разрезе по источнику столбец равен LEADS у Showroom и 0 у остальных, а SC бессмыслен. Не выводим (см. вопрос 1).

## Риски

- Источник лида в mefi можно поменять: прошлый месяц считается по текущему источнику на снапшот. Так же работают m2 и шоурумы, отдельно не лечим.
- UTM покрывают 12 % лидов и почти только Site: таблица кампаний про сайт, не про рекламу в целом. Строка доли об этом и говорит; в шаблоне подпись «au campanie», без выводов.
- В w6 кампаний выше порога 5 в неделю обычно одна; блок кампаний часто будет «nicio campanie…». Порог в конфиге, меняется без кода.
- Имена кампаний приходят из mefi как есть и идут в HTML Telegram: экранирование Jinja проверить в craft (`<`, `&` в UTM реальны).
- Окно w6 (семь ежедневных окон, Showroom включён) отличается от счёта лидов w1 (рабочий день, без Showroom): «din 26» в w6 не совпадёт с w1. Это сознательно: совпадает с w3.
- `load_lead_frame` читает ещё одно jsonb-выражение на все лиды снапшота (~3000): на время отчёта не влияет, но проверим на живой базе.

## Согласовано (28.09.2026)

1. Столбец «Vizite» из m7 убран: визит определяется по источнику Showroom, столбец тавтологичен.
2. w1 и Excel w12 переводятся на метку `without_source_label` из конфига отдельным коммитом `refactor(reports)` внутри фичи.
3. ADR не нужен: формулы не меняются. В TESTING.md уточнить: ADR при изменении формулы или существующих чисел эталона; добавление новых разделов эталона это запись в `docs/kpi-definitions.md` и `docs/PLAN.md`.
4. m7 и w6 включаются сразу (`enabled: true`), обкатка в тестовой группе с `DRY_RUN=1`.
5. Инструмент чата для разбивки это отдельный shape после этой фичи.
6. Прошлая неделя в w6: снапшот прошлого воскресенья; если его нет, первый более поздний успешный снапшот с пометкой в блоке (то же правило, что `period_snapshot_date` в чате); если нет никакого, «—», модуль не падает. Поэтому w6 читает не `context.week_ago` (он строго за воскресенье, для оферт w8), а отдельное поле контекста `previous_week` (`PreviousSnapshot`, дата снапшота видна в нём); раннер загружает его, только когда включён w6, и переиспользует уже загруженные кадры.
