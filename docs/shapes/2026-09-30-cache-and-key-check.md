# Shape: prompt caching в чате и проверка ключей mefi при старте

Две независимые задачи, два коммита. Кандидаты из `docs/PLAN.md`, раздел «Кандидаты».

Источники фактов: Context7 `/anthropics/anthropic-sdk-python` (top-level и блочный `cache_control`, TTL `5m`/`1h`, `usage.cache_creation_input_tokens`/`cache_read_input_tokens`), справочник prompt caching из скилла claude-api (29.09.2026): порядок префикса `tools → system → messages`; минимум кэшируемого префикса у `claude-sonnet-5` 1024 токена; запись 5m ×1,25 от входа, 1h ×2, чтение ×0,1; смена `tool_choice` сохраняет кэш tools и system, сбрасывает только кэш messages; смена `thinking`/`effort` сбрасывает кэш, поэтому они фиксированы.

---

## Часть 1. Prompt caching в чате

### Goal

Раунды tool-use одного вопроса и повтор стража читают описания инструментов и системный промпт из кэша; eval считает стоимость с раздельными ценами записи и чтения. Ответы, страж, маска не меняются.

### Что в запросе неизменно

`model_request` (`src/digest/chat/loop.py`) собирает: `tools` → `system` → `messages`.

- `tools`: `tool_definitions(config)` строится только из конфига (шоурумы, консультанты, описания из `modules.yaml`), даты в нём нет. Между вопросами и днями байт в байт одинаковый, пока не изменён конфиг или код.
- `system`: `templates/chat_system.md` с `$today` в первой строке. Меняется раз в сутки, в полночь по Бухаресту. При TTL 5 минут и 1 час кэш через полночь всё равно не дожил бы, поэтому дата кэш практически не ломает: первый вопрос нового дня пишет кэш заново, как и после любой паузы длиннее TTL. Дату не переносим.
- `messages`: вопрос, блок контекста уточнения (`chat_context.j2`), ответы модели, результаты инструментов. Меняются в каждом вопросе.
- `tool_choice`: `auto`, затем `none` на пределе вызовов и в повторе стража. По справочнику это сбрасывает только кэш messages, tools и system остаются.
- `thinking: disabled`, `model`, `max_tokens` постоянны.

Префикс tools + system ≈ 6 550 токенов (замер 29.09: 6 596 входных токенов первого раунда вместе с вопросом), выше минимума 1024.

### Approach

Один явный breakpoint: `system` передаётся списком из одного текстового блока с `cache_control: {"type": "ephemeral"}` (TTL 5 минут по умолчанию). Breakpoint на последнем блоке system кэширует tools и system вместе. `ChatAnswer` получает `cache_creation_input_tokens` и `cache_read_input_tokens`, суммируемые по раундам и повтору стража так же, как `input_tokens`; `None` из usage считается нулём (граница, ответ API). Каждый запрос к Anthropic пишет строку лога с номером раунда, `stop_reason` и четырьмя счётчиками usage: это и замер «до/после», и наблюдаемость на проде. Eval считает стоимость по четырём ценам.

### Files

- `src/digest/chat/loop.py`: `system` блоком с `cache_control`; накопление двух новых счётчиков в `first_attempt` и `guard_retry`; строка лога на каждый ответ API.
- `src/digest/chat/log.py`: запись двух новых счётчиков в `chat_questions`.
- `src/digest/db/schema.py` и миграция `0011_chat_cache_tokens.py`: `chat_questions.cache_creation_input_tokens`, `cache_read_input_tokens`, `Integer`, nullable (старые строки NULL = замера не было). `input_tokens` сохраняет смысл `usage.input_tokens` API: только некэшированный вход.
- `src/digest/acceptance/chat_eval.py`: `PRICES_PER_MILLION_TOKENS` из пары в четыре цены (вход, выход, запись кэша 5m, чтение кэша): для `claude-sonnet-5` и `claude-sonnet-5-5` 2,00 / 10,00 / 2,50 / 0,20; `EvalSummary` и строка таблицы «Токены in/out» печатают вход, запись, чтение, выход.
- Тесты: `tests/unit/test_chat_loop.py`, `tests/unit/test_chat_eval_grading.py` (или файл, где сейчас тест `summarize`), `tests/integration/test_chat_log.py`, `tests/integration/test_migrations.py` (upgrade с нуля уже покрыт).

### Schema / API changes

Миграция 0011: две nullable-колонки в `chat_questions`, downgrade удаляет их. Внешних API нет.

### Test plan

Seam: `model_request`, `answer_question` на заскриптованном Anthropic (MockTransport httpx2), `summarize` eval, строка `chat_questions`.

- `test_cached_prefix_is_identical_for_different_questions_on_one_day`: два `model_request` с разными вопросами, контекстом уточнения и `tool_choice` дают одинаковые `tools` и `system`; последний блок system несёт `cache_control`.
- `test_cached_prefix_has_no_date_outside_system`: `tool_definitions` двух разных `today` равны (страховка от даты, случайно попавшей в описания инструментов).
- `test_answer_sums_cache_tokens_across_rounds_and_guard_retry`: три ответа с разными usage (запись, чтение, повтор) → суммы в `ChatAnswer` ожидаемые, посчитанные руками.
- `test_usage_without_cache_fields_counts_as_zero`: заскриптованный ответ без полей кэша.
- `test_eval_cost_prices_cache_write_and_read_separately`: 1 000 000 входа, 1 000 000 записи, 1 000 000 чтения, 100 000 выхода → $2,00 + $2,50 + $0,20 + $1,00 = $5,70.
- `test_chat_question_row_stores_cache_tokens` (Postgres).

Живой замер (craft, шаг 0, ключ из `.env` пользователя): одна строка лога добавляется до `cache_control`; `eval chat --only` одного вопроса с двумя раундами (например `yesterday-leads`) до и после: вход/запись/чтение первого и второго раунда. Затем полный `eval chat`: M6 30/30, I4 12/12, стоимость до ($1,09 по прогону 29.09) и после. Это единственные траты: ≈ $0,05 на два `--only` и ≈ $0,25 на полный прогон.

### Ожидаемая экономия

Допущения: префикс P ≈ 6 550 токенов; полный eval 29.09 = 507 815 входа / 7 006 выхода; средний вход запроса ≈ 6,9k → ≈ 73 запроса на 42 вопроса (≈ 1,75 раунда на вопрос); вопросы eval идут подряд (медиана 5 с), пауз больше 5 минут нет.

| | Сейчас | С кэшем 5m |
|---|---|---|
| Полный eval (42 вопроса) | $1,09 | ≈ $0,24: 1 запись P ($0,016) + 72 чтения P ($0,094) + некэшируемый хвост 30k ($0,059) + выход ($0,070); −78 % |
| 30 вопросов в день, каждый вопрос после паузы > 5 минут | ≈ $0,026 на вопрос, $0,78 в день | ≈ $0,020 на вопрос (запись P $0,016, 0,75 чтения P $0,001, хвост и выход $0,003), $0,61 в день; −22 %, ≈ $5 в месяц |
| Уточнение в пределах 5 минут («Dar Cluj?») | ≈ $0,026 | ≈ $0,005 |
| Вопрос в один раунд (отказ, без инструмента) | ≈ $0,014 | ≈ $0,017: +25 % на запись без чтения |

На проде выигрыш держится на втором раунде и повторе стража: кэш между вопросами при 5m живёт только у уточнений. 30 в день это лимит, не реальный трафик.

### Tradeoffs / alternatives considered

- **TTL 1 час.** Запись ×2. Окупается, если вопросы идут с паузами 5–60 минут: при 30 вопросах за 10 часов оценка ≈ $0,28 в день против $0,61. При редких вопросах (несколько в день через часы) дороже, чем без кэша. Реального трафика ещё нет (чат только в тестовой группе), решение по данным: после недели на проде посмотреть паузы между вопросами в `chat_questions.created_at` и долю чтения в новых колонках. Переключение одной строкой в `loop.py`.
- **Top-level автоматический `cache_control`.** Ставит breakpoint на последний блок, то есть на хвост с вопросом и результатами: каждый запрос платит ×1,25 за хвост, который читается только в следующем раунде того же вопроса, а `tool_choice: none` в повторе стража всё равно сбрасывает кэш messages. Выигрыш на хвосте ≈ 0,6k токенов не стоит лишней записи. Отклонён.
- **Дату из system в сообщение пользователя, второй breakpoint на последнем инструменте.** Сохранил бы tools + правила промпта через полночь, но TTL полночь не переживает; меняет порядок промпта, который eval подтвердил 30/30. Отклонён.
- **`input_tokens` в `chat_questions` как сумма трёх полей, без миграции.** Смешивает цены ×1, ×1,25, ×0,1 в одном числе, стоимость по таблице не восстановить. Отклонён.

### Риски

- Цены записи и чтения для `claude-sonnet-5` взяты из справочника (запись 5m ×1,25 = $2,50, чтение ×0,1 = $0,20), счёт в консоли Anthropic не сверялся. Сверить после первого полного прогона.
- Невидимая инвалидация: если в описания инструментов когда-нибудь попадёт дата или неупорядоченный set, чтение молча упадёт до нуля. Ловит тест равенства префикса и строка лога (`cache_read` = 0 во втором раунде).
- Кэш общий на workspace ключа: eval и прод на одном ключе читают друг у друга. Вреда нет, но замер «первый раунд пишет» после свежего прогона может показать чтение.
- Недетерминированность модели: eval после правки может дать 29/30 по случайной причине, не из-за кэша. Кэш не меняет вход модели ни на байт; повтор `--only` провала решает.

## Часть 2. Проверка ключей mefi при старте

### Goal

Сообщение о старте в служебный бот говорит, живы ли оба ключа mefi: «Бот запущен, версия abc1234, DRY_RUN=1. Ключи mefi: leads ✓, clients ✓.» Отозванный ключ (как 29.09 с `leads:read`) виден сразу после рестарта, а не в 19:00.

### Approach

`MefiClient.check_key(path)`: один `_search_page` с `per_page=1` через общий пейсер процесса (≥ 1,2 с между запросами, 429 → `Retry-After`, как везде). Для лидов фильтр `{"lifecycle": ["active","lost","junk"]}` (обязательный по ловушке пустого body), для клиентов `{}`. 401/403 уже превращаются в `MefiKeyRejected` с текстом из 5bbb03d. `check_mefi_keys(snapshot_sources)` в `app.py` проверяет оба ключа последовательно под общим таймаутом 20 с и отдаёт строку: `✓` на успех, `✗` на `MefiKeyRejected` (под строкой текст исключения: какой ключ, что сделать), «не проверен (<describe_error>)» на любую другую ошибку и таймаут. `run_app` вызывает её перед `notify_ops(startup_announcement(...))`; `startup_announcement` принимает строку ключей. Старт не блокируется: исключения не выходят наружу, дальше идут поздний снапшот и планировщик как сейчас.

Выполняется и при `DRY_RUN=1`: это чтение разрешёнными эндпоинтами, а ноутбук с `DRY_RUN=1` как раз то место, где ключ меняют и проверяют.

### Files

- `src/digest/mefi/client.py`: `MefiClient.check_key`.
- `src/digest/app.py`: `check_mefi_keys`, параметр строки ключей у `startup_announcement`, вызов в `run_app`.
- `tests/integration/test_mefi_client.py`: `check_key` через respx.
- `tests/unit/test_app.py`: формат строки и сообщения о старте.

### Schema / API changes

Нет. Новых вызовов mefi сверх разрешённых нет: `POST /leads/search` и `POST /clients/search`, два запроса на старт.

### Test plan

Seam: `MefiClient.check_key` (respx), `check_mefi_keys` на `SnapshotSources` с respx, `startup_announcement`.

- `test_check_key_sends_one_page_of_one_with_all_lifecycles`: тело запроса лидов `per_page=1` и три lifecycle; клиентов пустой `filters`.
- `test_check_key_raises_key_rejected_on_401`: текст про `leads:read` и `MEFI_API_KEY`.
- `test_startup_line_marks_rejected_key_and_keeps_other`: leads 401, clients 200 → «Ключи mefi: leads ✗, clients ✓.» и под ней текст отказа.
- `test_startup_line_reports_unchecked_key_on_timeout`: зависший ответ → «не проверен», без исключения.
- `test_startup_announcement_contains_keys_line`: правка существующего теста.

### Tradeoffs / alternatives considered

- **Фоновая задача и отдельное сообщение.** Не задерживает старт ни на секунду, но даёт второе сообщение, а просили одну строку в стартовом. Задержка старта 2,4 с при здоровом mefi, до 20 с при висящем, при том что поздний снапшот после неё и так идёт минуты. Отклонён.
- **Проверка частью позднего снапшота.** Поздний снапшот запускается не на каждом старте (только после 19:00 без success), поэтому ключ после утреннего рестарта не проверялся бы. Отклонён.
- **Не выполнять в DRY_RUN.** DRY_RUN ограничивает отправку в продовую группу, а не чтение mefi. Отклонён.

### Риски

- Рестарт в цикле (падение сразу после старта) даёт два запроса на рестарт; при 1 req/s по IP это не бан. Пейсер общий, поэтому одновременный с проверкой снапшот не превысит темп.
- 429 при проверке: пейсер ждёт `Retry-After`; при долгом бане сработает таймаут 20 с и строка «не проверен».

## Согласовано (29.09.2026)

1. Колонки кэша в `chat_questions` (миграция 0011): да.
2. Сводка `eval chat`: вход, запись кэша, чтение кэша и выход отдельными числами, плюс стоимость по четырём ценам.
3. Отказ ключа при старте: только строка в стартовом сообщении ops, без отдельного алерта; при ✗ строка начинается с «⚠️».
4. TTL 5 минут; 1 час рассматривается после недели в Prod по паузам в `chat_questions`.
5. Цены кэша сверить с консолью Anthropic после первого полного eval; записать в PLAN.
