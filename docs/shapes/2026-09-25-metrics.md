# Shape: metrics/ (KPI по брифу, provisional SPI, m5, доп. метрики)

Статус: подтверждён 25.09.2026 с ответами ниже. Источники истины: `docs/kpi-definitions.md`, ADR-002, `config/kpi.yaml`, `config/status-mapping.yaml`.

## Цель

Один набор чистых функций над DataFrame снапшота лидов даёт счётчики и 9 KPI по компании, шоуруму и консультанту; те же функции потом вызывают отчёты и чат. `test_kpi_matches_etalon` сверяет их с `expected_by_agent` по 6 консультантам с точностью 1e-9.

## Подход

- **Кадр лидов.** `load_lead_frame(engine, tenant_id, snapshot_date, config)`, async: SQLAlchemy Core `select` колонок `lead_snapshots` без `raw`, затем чистая `prepare_lead_frame(rows, config)`. Она переводит timestamptz в Europe/Bucharest, убирает лиды тестовых аккаунтов и добавляет флаги: `is_clienti` (category WON), `is_irelevant` (loss_reason IRELEVANT), `is_partnership`, `is_nu_a_raspuns`, `is_buget`, `is_produs_nepotrivit` (по loss_reason), `is_ofertat` (`ofertat is True`, null → False), `is_showroom_visit` (`source_name` из `sources.showroom_visit` конфига). Флаги только из category/loss_reason/ofertat, статусы в коде не упоминаются. Эталонный тест вызывает ту же `prepare_lead_frame`, только строки берёт из фикстуры.
- **Счётчики и KPI.** `Period(start, end)`, frozen dataclass, полуинтервал, aware datetime. `lead_counts(df, period, analysis_date) -> LeadCounts` (11 полей, имена как в эталоне). `lead_counts_by_showroom(...) -> dict[str, LeadCounts]` по полю лида `showroom`. `lead_counts_by_manager(..., roster) -> dict[int, LeadCounts]` по `assigned_to_id`, только `active: true`. `kpis_from(counts) -> Kpis` (9 полей `float | None`, деление на ноль → None). Реализация: маска периода плюс `groupby().sum()` по флагам, без циклов по строкам.
- **Provisional.** `metrics/spi.py`: `kpi_scores(kpis, settings)`, `irr_penalty`, `spi`, `spi_level`, `recommendation_key`. Ступени и очки переезжают в `config/kpi.yaml` (секция `scores`), код только проходит ступени сверху вниз. `null` → очки нижней ступени (для штрафа IRR это −10). Отчёты MVP модуль не импортируют.
- **m5.** `manager_cockpit_table(df, period, analysis_date, roster, settings) -> DataFrame`: строка на активного консультанта (id, имя, шоурум из managers.yaml), 11 счётчиков, 9 KPI и `<kpi>_meets_target: bool | None`. Цели в новой секции `targets` в `kpi.yaml` (значение и направление), первые ступени плюс L2O 50 %, O2C 20 %.
- **Доп. метрики** (`metrics/extra.py`): `overdue_revenire(df, today)` отдаёт id лидов, у которых `data_revenire <= today` и `status_changed_at` null или раньше `data_revenire`; `cohort_conversion(df, month)` отдаёт `CLIENTI / USEFUL` по лидам месяца на дату снапшота; `period_delta(now, prev)` при `prev == 0` возвращает None.
- **Неизвестные консультанты.** `unknown_manager_ids(df, roster) -> set[int]`: метрики не логируют, алерт шлёт вызывающий код.

## Схема / API

Миграций нет. Новый публичный API: функции выше. `kpi.yaml` получает `scores` и `targets`; загрузка строгая, как у остальных конфигов.

## Тест-план

Швы: публичные функции `metrics/` и строка `lead_snapshots`.
- `test_kpi_matches_etalon`: `prepare_lead_frame` на строках фикстуры, ростер из секции `managers`, период 01.05–17.06.2026, `analysis_date` 2026-06-27; `counts` точно, `kpi` с `abs=1e-9`, None против None, для всех 6. Первым красным.
- Frame: лиды тестового аккаунта исключены; `ofertat` null → не оферта; SPAM и IRELEVANT дают `is_irelevant`; UNMAPPED входит в LEADS без флагов; время переведено в Бухарест.
- KPI: PARTNERSHIP вне LEADS; SC считает только клиентов среди визитов; деление на ноль даёт None для каждого KPI; граница периода (лид ровно в `end` не входит, 19:00 по Бухаресту); висящая оферта ровно на 14-й день не входит, на 15-й входит; `last_contact_at` null не входит; неактивный консультант не попадает в разрез.
- SPI: каждая ступень каждого KPI на границе (≥ и ≤); null → нижняя ступень; SPI не ниже 0; уровни на 59/60, 89/90; порядок цепочки рекомендаций.
- Cockpit: одна строка на активного консультанта, `meets_target` учитывает направление, None при None.
- Extra: revenire на границе `today`, смена статуса после даты снимает просрочку; когорта; дельта при 0.
- Интеграция (testcontainers): `load_lead_frame` читает только свой tenant и дату, типы колонок совпадают с кадром из фикстуры.

## Альтернативы

- **Агрегация в SQL.** Отвергнута: PRINCIPLES требует чистых функций над DataFrame, а чату и отчётам нужна одна функция без второй реализации на SQL.
- **Возвращать dict вместо dataclass.** Отвергнута: mypy не ловит опечатки в ключах, а ключ с опечаткой даёт неверную цифру. Сравнение с эталоном идёт через `asdict`.
- **Очки ступеней в коде.** Отвергнута: механика provisional, калибровка не должна требовать правки кода.

## Решения по открытым вопросам (25.09.2026)

1. `is_duplicate` в KPI v1 не учитывается; пересмотреть после оценки доли дублей в снапшотах.
2. Рекомендация при `LEADS = 0` — None. KPI = null: условие цепочки не срабатывает.
3. Просроченные revenire: ACTIVE, ACTIVE_FOLLOWUP, LOST · STAND_BY, UNMAPPED; WON, PARTNERSHIP и остальные причины LOST исключены (Stand BY — главный случай, бриф §3).
4. `lead_counts_by_showroom` возвращает `dict[str | None, LeadCounts]`, ключ None — «без шоурума»; показывать ли строку, решает отчёт.

Дополнения: все счётчики за период по `created_at`, `Period` — полуинтервал `[start, end)`. Тест `unknown_manager_ids`: id вне ростера попадает, null не попадает. Секция `managers` эталона, `scores`/`targets`/`recommendations` в `kpi.yaml` и pandas — отдельным первым коммитом.
