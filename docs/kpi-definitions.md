# KPI — определения, формулы, пороги

Формулы — по `docs/brief.md` §3 (ADR-002). `SB KPi.xlsx` составлен через ИИ, из него берутся только лиды для эталона; расхождения с workbook перечислены в конце. Пороги и цели — `config/kpi.yaml`. Изменение формулы или порога — только через ADR и пересборку эталона.

Считаются по консультанту, по шоуруму и по компании за период.

## Признаки лида

| Признак | Определение |
|---|---|
| категория | по `status.name` из `config/status-mapping.yaml` (инвариант 4), не подстрокой |
| `is_clienti` | категория `WON`: `status.name = Clienți`. `converted_at` в счёт не идёт, расхождение с ним — алерт снапшота |
| `is_irelevant` | `LOST · IRELEVANT`: IRELEVANT, SPAM |
| `is_excluded_from_useful` | причина LOST с `excluded_from_useful: true` в `status-mapping.yaml` (сейчас только IRELEVANT) |
| `is_excluded_from_leads` | `PARTNERSHIP` (DESIGNER, INFLUENCER) при `excluded_from_leads: true` |
| `is_unmapped` | категория `UNMAPPED` |
| `is_nu_a_raspuns` | `LOST · NU RASPUNS` |
| `is_buget` | `LOST · BUGET` |
| `is_produs_nepotrivit` | `LOST · PRODUS NEPOTRIVIT` |
| `is_ofertat` | кастомное поле `Ofertat` (field_id 20) = `✅DA` |
| `is_showroom_source` | источник из `sources.showroom_visit` (Showroom): любой приход, в том числе партнёрский и revenire |
| `is_showroom_revenire` | `is_showroom_source`, не PARTNERSHIP, контакт совпал с лидом, созданным раньше начала собственного ежедневного окна лида (ADR-007, «Визит» ниже) |
| `is_showroom_visit` | `is_showroom_source`, не PARTNERSHIP, не `is_showroom_revenire` (ADR-007) |
| консультант | `assigned_to.id` → `config/managers.yaml`, имя не сравнивается |

Лиды без консультанта входят в итог по компании, но ни в одну строку по консультантам.

Разрез по шоуруму: строки для каждого значения `showrooms` из `status-mapping.yaml`, затем для каждого значения поля Showroom вне этого списка (отдельной строкой, чтобы лиды не пропали из разреза молча), затем строка «без шоурума» для `null`.

## Базовые множества (за период, по `created_at` лида)

| Обозначение | Определение |
|---|---|
| `LEADS` | лиды с `created_at` в периоде, **кроме** `is_excluded_from_leads` (PARTNERSHIP) и лидов тестовых аккаунтов (`test_account: true`) |
| `IRR_LEADS` | `LEADS` с `is_irelevant` |
| `USEFUL` | `LEADS` без `is_excluded_from_useful`; при текущем конфиге `LEADS − IRR_LEADS` (= все − IRELEVANT − PARTNERSHIP, бриф §3) |
| `CLIENTI` | `LEADS` с `is_clienti` |
| `OFFERS` | `LEADS` с `is_ofertat` |
| `NAR` | `LEADS` с `is_nu_a_raspuns` |
| `BUGET` | `LEADS` с `is_buget` |
| `PNP` | `LEADS` с `is_produs_nepotrivit` |
| `SHOWROOM_VISITS` | `LEADS` с `is_showroom_visit`: без revenire (ADR-007); партнёры и так вне `LEADS` |
| `UNMAPPED` | `LEADS` с категорией `UNMAPPED` (инвариант 4); входят в `LEADS` и `USEFUL` и считаются отдельно |
| `ACTIVE_OFFERS_14` | `OFFERS` с категорией `ACTIVE` или `ACTIVE_FOLLOWUP` (лид в работе), `analysis_date − date(last_contact_at) > 14` дней; `last_contact_at = null` → не входит. LOST, WON, UNMAPPED с офертой в истории не висят (ADR-005) |

`analysis_date` — дата расчёта отчёта, дата `last_contact_at` берётся в Europe/Bucharest. Порог дней — `active_offer_stale_days`. `status_changed_at` не используется: в mefi он `null`, если статус задан при создании лида.

## KPI (отчёты MVP: m5 и режим вопросов)

| KPI | Название | Формула | Цель |
|---|---|---|---|
| SCR | Sales Conversion Rate | `CLIENTI / USEFUL` | > 10 % |
| L2O | Lead to Offer | `OFFERS / USEFUL` | > 50 %, информативно |
| O2C | Offer to Client | `CLIENTI / OFFERS` | > 20 %, информативно |
| CDR | Contact Discipline Rate | `(LEADS − NAR) / LEADS` | > 90 % |
| PLR | Price Lost Rate | `BUGET / (LEADS − IRR_LEADS − NAR)` | < 25 % |
| SC | Showroom Conversion | `count(CLIENTI ∩ SHOWROOM_VISITS) / count(SHOWROOM_VISITS)`; revenire ни в числителе, ни в знаменателе, конверсия визита это только сам лид визита (ADR-007); атрибуция продажи по контакту к первому визиту это отдельный ADR | > 20 % |
| PFR | Product Fit Rate | `PNP / USEFUL` | < 10 % |
| ACR | Active Control Rate | `ACTIVE_OFFERS_14 / LEADS` | < 20 % |
| IRR | Irrelevant Rate | `IRR_LEADS / LEADS` | ≤ 20 % |

Цели — секция `targets` в `config/kpi.yaml`: первые ступени порогов (`scr_elite`, `cdr_minim`, `plr_maxim`, `sc_perfect`, `pfr_perfect`, `acr_perfect`, `irr_acceptabil`) плюс L2O и O2C. Они тоже `provisional`, но показываются как ориентир рядом с фактом. Цель выполнена при ≥ (↑) или ≤ (↓) включительно, как ступени баллов; KPI = null → «—».

Доли не округляются до вывода. **Деление на ноль:** метрика `null`, в отчёте и в ответе чата «—».

**Период:** все счётчики фильтруются по `created_at` лида, полуинтервал `[start, end)`, Europe/Bucharest.

`is_duplicate` в KPI v1 не учитывается; пересмотреть после оценки доли дублей в снапшотах.

## Предварительно, не показывать до калибровки (ADR-002)

Механика ниже пришла из workbook и не согласована с владельцем. Функции в `metrics/` есть, пороги в `config/kpi.yaml` (`status: provisional`), но в отчёты MVP и в ответы чата SPI, баллы, уровни SPI и рекомендации не выводятся. Ступени SCR в m4 (раздел «Месячное окно») это не уровни SPI: их подписи не совпадают с названиями `levels` из `kpi.yaml`, это проверяется при загрузке конфига. Калибровка — по 2–3 месяцам снапшотов плюс Excel 2024–2025, отдельным ADR. Ступени, очки и цепочка рекомендаций — секции `scores`, `irr_penalty`, `recommendations` в `config/kpi.yaml`. KPI = `null` → очки нижней ступени (штраф IRR −10), условие рекомендации не срабатывает; при `LEADS = 0` рекомендации нет.

### Баллы

Проверка сверху вниз, первая выполненная ступень.

| KPI | Ступень 1 | Ступень 2 | Ступень 3 | Иначе | Макс. |
|---|---|---|---|---|---|
| SCR ↑ | ≥ `scr_elite` (10 %) → 30 | ≥ `scr_bine` (7 %) → 24 | ≥ `scr_minim` (5 %) → 18 | 10 | 30 |
| CDR ↑ | ≥ `cdr_perfect` (95 %) → 20 | ≥ `cdr_minim` (90 %) → 16 | ≥ `cdr_contact_floor` (80 %) → 10 | 5 | 20 |
| PLR ↓ | ≤ `plr_perfect` (20 %) → 20 | ≤ `plr_maxim` (25 %) → 16 | ≤ `plr_problema` (35 %) → 10 | 5 | 20 |
| SC ↑ | ≥ `sc_perfect` (20 %) → 15 | ≥ `sc_bine` (15 %) → 12 | ≥ `sc_minim` (10 %) → 8 | 4 | 15 |
| PFR ↓ | ≤ `pfr_perfect` (10 %) → 10 | ≤ `pfr_bine` (15 %) → 8 | ≤ `pfr_maxim` (20 %) → 5 | 2 | 10 |
| ACR ↓ | ≤ `acr_perfect` (20 %) → 5 | ≤ `acr_maxim` (30 %) → 3 | — | 1 | 5 |

Штраф IRR: ≤ `irr_acceptabil` (20 %) → 0; ≤ `irr_atentie` (30 %) → −5; иначе −10.

`SPI = max(0, сумма баллов + штраф IRR)`, максимум 100.

### Уровни (`config/kpi.yaml` → `levels`)

| SPI | Уровень |
|---|---|
| ≥ 90 | Elite |
| ≥ 80 | Gold |
| ≥ 70 | Silver |
| ≥ 60 | Bronze |
| < 60 | Coaching |

### Главная рекомендация

Первое выполненное условие сверху вниз. Текст RO из workbook, RU — в `templates/recommendations.{ro,ru}.yaml`.

| Приоритет | Условие | Текст RO |
|---|---|---|
| 1 | IRR > `irr_atentie` (30 %) | Verifică utilizarea statusului IRELEVANT |
| 2 | CDR < `cdr_minim` (90 %) | Coaching disciplină contact |
| 3 | PLR > `plr_maxim` (25 %) | Coaching preț / valoare |
| 4 | SCR < `scr_minim` (5 %) | Coaching închidere |
| 5 | ACR > `acr_perfect` (20 %) | Prioritate follow-up oferte active |
| 6 | иначе | Performanță stabilă |

## Дополнительные метрики (не из SPI)

| Метрика | Формула |
|---|---|
| Speed-to-lead | Формула брифа недействительна: заметки через API недоступны, а `last_contact_at` и `status_changed_at` по одному снапшоту первое касание не дают (`docs/mefi-api-notes.md`, 24.09.2026). Переопределяется в ADR-003 перед включением w5. В MVP w5 выключен. |
| Просроченные revenire | лиды с кастомным `Data revenire < today` (строго, ADR-004) и без изменения статуса после этой даты (`status_changed_at` null или раньше `Data revenire`). Категории: ACTIVE, ACTIVE_FOLLOWUP, LOST · STAND BY, UNMAPPED; WON, PARTNERSHIP и остальные причины LOST не входят |
| Когортная конверсия | `CLIENTI из лидов месяца M на дату D / USEFUL месяца M` — считается по снапшоту на D |
| Дельта к периоду | `(X_now − X_prev) / X_prev`; при `X_prev = 0` → «n/a» |
| Разница к периоду или цели | `X − база` со знаком (`value_difference`); у KPI в процентных пунктах; база или X null → нет значения. Чат: `compare_periods` (`difference`, `direction`, `change`), `manager_kpi` (`vs_target`) |
| Доля причины потерь | `потери причины / все потери` периода (`LossReasons.reason_share`), в разрезе шоурума от потерь шоурума (`showroom_reason_share`); 0 потерь → нет значения. Чат: `loss_reasons` |

## Ежедневные проверки (d2–d6, shape `docs/shapes/2026-09-25-daily-d2-d6.md`)

Окно — суточное, 19:00 вчера → 19:00 сегодня по Europe/Bucharest, [start, end). Функции в `src/digest/metrics/daily_checks.py`. «Не взят» — лид на консультанте с `not_taken: true` в `config/managers.yaml` (Marketing Sofa) или без `assigned_to`; такие лиды идут отдельной группой.

| Модуль | Формула |
|---|---|
| d2 лиды без касания | `created_at` в [конец окна − `lookback_days`, конец окна), возраст от конца окна > `threshold_hours`, не PARTNERSHIP, источник не `sources.showroom_visit`. Без касания: `status_changed_at` null ∧ `last_contact_at − created_at ≤ touch_tolerance_seconds` (60 с; пустой или раньше `created_at` тоже без касания) ∧ не `ofertat` ∧ `created_by.id` не консультант с `active: true`. Не взятый лид попадает в d2 независимо от касаний, заголовок блока «без касания или не взятые». `created_by.id` вне `managers.yaml` идёт в общий алерт с неизвестными `assigned_to.id`. Итог: число лидов и возраст самого старого по всем группам; по группе: число лидов и возраст самого старого в ней, в целых часах |
| d3 просроченные revenire | «Просроченные revenire» (ниже в «Дополнительных метриках»), итог: число лидов и максимальная просрочка `today − Data revenire` в днях по всем группам; по группе то же внутри группы. Отдельный блок «Fără Data revenire» внутри d3 (`missing_followup_date`, шаблон `missing_followup_date.j2`, параметр d3 `missing_followup_date`, вопрос П5): флаг кадра `is_followup_status` (категория ACTIVE_FOLLOWUP или причина LOST с `followup_field`: Revenire 1/2/3, Stand BY; тот же флаг входит в условие просроченных), `created_at ≥ leads_created_from` (status-mapping.yaml, 01.06.2026, 00:00 Бухарест), статус стоит дольше `missing_followup_min_age_hours` (24) до конца окна: от `status_changed_at`, при null от `created_at`, ровно 24 ч не входит; это охват. Пустым считается `Data revenire` = null или пустая строка. Лид охвата, у которого поле не прочитано (`data_revenire_problem` снапшота: `missing` поля нет, `name_mismatch` под field_id другое имя, `unexpected_value` не дата), в блок не входит; если поле не прочитано у всех лидов охвата, вместо блока «Date Data revenire indisponibile» и ошибка в служебный бот (инвариант 6). PARTNERSHIP не входит по категории, тестовый аккаунт убран в кадре. Группы как у просроченных (`count_and_max_by_manager`): по `assigned_to_id`, имя из лида, не взятые первыми с подписью «Nepreluate», дальше по числу лидов и имени. Ссылки самые старые по времени статуса; блок отдельный, со своими 10 ссылками (`lead_links.limit`) и «și încă N». Пусто: «Fără Data revenire: nu». Чат: `overdue_followups` отдаёт тот же результат в `missing_followup_date` (при выключенном параметре не отдаёт). Замер по снапшоту 28.09: 40 лидов, 5 консультантов; ещё 30 получили статус в последние 12 ч окна и войдут на следующий день |
| d4 висящие оферты | `ACTIVE_OFFERS_14` по всем лидам снапшота (без ограничения периода), по шоурумам. Дельта итога к вчера только при снапшоте ровно за вчера (`comparable_previous`, то же правило, что в d1), иначе «—»; при нуле висящих оферт ненулевая дельта выводится |
| d5 сайт молчит | лидов строки web d1 с источником из `sources.site` в окне 0, а среднее по `site_average_days` (7) предыдущим окнам (по `created_at` сегодняшнего кадра) ≥ `site_zero_min_average` |
| d5 всплеск IRELEVANT | у группы лидов с причиной IRELEVANT, отмеченных в окне (`status_changed_at`, а если он null — `created_at`), ≥ `irelevant_spike_min`; группа «не взят» первой |
| d6 тот же день недели | лиды: сумма пяти строк Leads d1 в окне сегодня и в окне `report_date − 7`, оба по сегодняшнему кадру. Контракты: `converted_at` в каждом окне (ADR-004) |

**Ссылки на лиды в d2–d4** (shape `docs/shapes/2026-09-27-lead-links.md`): метрики отдают id лидов блока и каждой группы, самые старые первыми, при равенстве по id: d2 по `created_at`, d3 по `data_revenire` (самая просроченная первой), d4 по `last_contact_at`. Формулы счётчиков не меняются, число id группы равно её счётчику. В отчёт идут ссылки на 10 самых старых лидов всего блока (`lead_links.limit`), у группы её ссылки из этой десятки и «și încă N» за остальные; группа без лидов в десятке без ссылок.

**d1 строки** (ADR-006, `metrics/daily.py`, окно то же). Строки Leads взаимоисключающие, по `created_at` в окне:
- Designer/Colaboratori: новые лиды с категорией PARTNERSHIP или источником из `sources.partner` плюс лиды, чья категория стала PARTNERSHIP по разнице со снапшотом ровно за вчера (лид, созданный в окне, считается один раз). Без вчерашнего снапшота только новые лиды, сноска.
- Лид с источником `sources.showroom_visit` (не партнёрский): `is_showroom_revenire` → Alte/Showroom (revenire), `is_showroom_visit` → Vizita in showroom («Визит» ниже). Статус лида на визит не влияет.
- Alte/Showroom (revenire): `sources.other`, `sources.repeat_client` (Client Fidel), источники вне всех групп (алерт) и Showroom-revenire.
- Oferta: переход `is_ofertat` по разнице со снапшотом ровно за вчера, иначе «—».
- Contract Cantitate: новые клиенты mefi (`client_snapshots` за дату отчёта) с `created_at` в окне и не раньше `clients.contracts_count_from`, по полю Showroom клиента. Нет успешного снапшота клиентов → «—», сноска, алерт.

**Contract Cantitate в d1 считает новых клиентов mefi, d6 и w8 converted_at лидов; расхождение это клиенты без лида.**

**Визит** (ADR-007, `metrics/visits.py`). Одно правило для d1, w2, w8, w12, KPI и чата. Revenire: Showroom-лид (не PARTNERSHIP), чей непустой ключ телефона или e-mail (HMAC, `digest/contact_keys.py`) совпал с лидом того же снапшота, созданным раньше начала собственного ежедневного окна лида (`daily_window` дня, чьё окно содержит `created_at`). Остальные непартнёрские Showroom-лиды это визиты. Граница по окну лида, а не по периоду отчёта: неделя (w2, w6, w8), месяц и периоды чата состоят из ежедневных окон и на одном снапшоте равны сумме дней d1 по построению. С уже отправленными d1 сумма может разойтись не из-за правила визита, а потому что каждый d1 читал свой снапшот (лид позже ушёл в PARTNERSHIP, ранний лид удалён в mefi). Лид без ключей (снапшоты до миграции 0005) revenire не бывает.

Факт по снапшоту 28.09.2026: mefi дубли разрешает (4 лида `is_duplicate`), телефон делят 34 лида из 3056, пар Showroom–Showroom нет, `Data revenire` заполнена у 1441 лида. Повторный приход новым лидом не заводится, поэтому revenire по контакту ожидаемо ≈ 0. Метрика повторного визита по изменению существующего лида это отдельный shape после ответа владельца.

**Повторный приход в mefi не фиксируется** (уточнение пользователя 29.09.2026). Статусы Revenire 1/2/3 это первое, второе, третье касание менеджера с клиентом, а не визит. Строка продавцов «Leads Alte/Showroom (revenire)» означает повторный приход в шоурум (например, подписать договор), и в mefi его нет ни статусом, ни полем. Поэтому revenire по контакту ловит только редкий повторный лид, а ноль значит «нет данных», а не «никто не вернулся»: w2 показывает `Reveniri: N` только при N > 0, d1 под блоком одной сноской пишет «Revenirile în showroom nu sunt înregistrate în CRM și nu sunt incluse.» (`templates/seller_format_report.j2`). Вопрос В1 в `docs/owner-questions.md`.

**Лиды d6 и d1.** d6 берёт `lead_row_flags`, то есть новые лиды окна с правилом revenire, но без переходов в PARTNERSHIP: при таком переходе «Lead-uri azi» в d6 меньше итога Leads d1.

## Недельные окна (w1–w4, w8, w12, shape `docs/shapes/2026-09-25-weekly.md`)

Отчёт за неделю Пн–Вс читает снапшот за воскресенье. Функции в `metrics/weekly.py`.

- **Рабочий день лида** (`working_days`): время created_at по Бухаресту в [`working_hours.start`, `working_hours.end`) = [10:00, 19:00) → этот день, любое другое (в том числе 00:00–09:59) → следующий календарный день. Правило ручного понедельничного отчёта, `docs/samples/weekly-manual-report-2026-07.md`.
- **Неделя лидов** (w1, w12, строка лидов w8): лиды с рабочим днём Пн–Вс, источник из `sources.showroom_visit` исключён (`is_showroom_source`: визит, revenire и партнёрский Showroom). Интервалом created_at это не выражается: воскресенье 00:00–10:00 уходит в следующую неделю.
- **Окно недели** (w2, w3, w4, визиты и контракты в w8): [Вс 19:00 прошлой недели, Вс 19:00) = семь ежедневных окон d1. День визита в w2 и на листе «Vizite» = день D, чьё окно `daily_window(D)` содержит created_at.
- **w2**: визиты `is_showroom_visit` в окне недели (без партнёров и revenire, ADR-007), итог равен сумме Vizita d1 за семь дней. Строка `Reveniri: N` (число `is_showroom_revenire` в окне) только при N > 0: повторный приход в mefi не фиксируется, ноль означает отсутствие данных («Визит»).
- **w1, колонки источников**: только встреченные за неделю, по убыванию итога, при равенстве по алфавиту, «(fără sursă)» последней. Шоурумы: из `showrooms`, затем не из списка, затем «(fără showroom)».
- **w3**: `lead_counts` и `kpis_from` на окне недели, когорта на дату снапшота: оферты и контракты ещё будут расти.
- **w4**: LOST по ключам `LOST.reasons`: status_changed_at в окне недели; лид, созданный в окне сразу со статусом потери (status_changed_at = null), считается по created_at.
- **w8**: обе недели по воскресному снапшоту (created_at и converted_at не меняются). Оговорка: если лид удалили в mefi или сменили ему источник на Showroom или обратно между двумя воскресеньями, «прошлая неделя» в w8 разойдётся с w1, отправленным неделю назад. Контракты по converted_at. Оферты недели = разница со снапшотом ровно за прошлое воскресенье (`transition_flags`), иначе «—»; изменение оферт к прошлой неделе не считается: нужен снапшот двухнедельной давности. Изменение = (эта − прошлая) / прошлая; прошлое значение 0 даёт «—» всегда, в том числе 0 против 0.

## Месячное окно (m2–m5, m8, m11, m19, shape `docs/shapes/2026-09-25-monthly.md`)

Отчёт за месяц уходит 1-го числа в 09:00 и читает снапшот за последний день месяца. Функции в `metrics/monthly.py`. Все окна отчётов заканчиваются в 19:00 дня снапшота.

- **Окно месяца** (`month_window`): [последний день прошлого месяца 19:00, последний день месяца 19:00) = ежедневные окна d1 всех дней месяца. Лид, созданный последним днём месяца после 19:00, уходит в следующий месяц: в снапшот последнего дня он не попал, и календарное окно потеряло бы его навсегда.
- **m2, m4**: `lead_counts` и `lead_counts_by_showroom` на окне месяца, когорта на дату снапшота. Уровень SCR в m4: первая ступень из `params.levels` модуля m4 (имена порогов `kpi.yaml`) с SCR ≥ порога; ниже всех ступеней → `below_label`; SCR = null → «—». Подписи ступеней RO/RU в `params` модуля, по `docs/report-menu.md` m4. Ступень воронки CLIENTI в m2, m5, m19 подписана «Clienți» (статус на дату снапшота у лидов месяца), слово «Contracte» только у m3 (converted_at). Отметка цели по `targets.scr`, как в m5.
- **m3**: шесть месяцев, последний отчётный, все из одного снапшота. Лиды месяца = LEADS по created_at, контракты = лиды с converted_at в окне месяца (как d6 и w8), без процента: контракты месяца и лиды месяца это разные когорты. Когортная конверсия относится к m9.
- **m5**: `manager_cockpit_table` на окне месяца.
- **m8**: правило w4 на окне этого и прошлого месяца, оба по одному снапшоту. Лид, у которого после потери в прошлом месяце статус сменился ещё раз, из прошлого месяца выпадает: status_changed_at хранит только последнее изменение. Изменение = (этот − прошлый) / прошлый; прошлое значение 0 даёт «—». Доля причины (Pondere) = потери по причине / все потери этого месяца; потерь нет → «—». Доля строки итога = итог / итог (1 или «—»).
- **m19, лист «Lead-uri luna»**: те же лиды, что LEADS компании в m2; колонка «Zi» = день created_at по Бухаресту.
- **m11 «Clienți care revin»** (shape `docs/shapes/2026-09-28-repeat-clients.md`, `monthly_repeat_clients`): клиенты месяца = лиды категории WON с `converted_at` в окне месяца. Клиент повторный по одной из двух причин: (1) «telefon/e-mail»: его непустой ключ телефона или e-mail (`contact_phone_key`, `contact_email_key`, ADR-006) совпал с другим лидом WON, чей `converted_at` строго раньше; равные `converted_at` друг друга повторными не делают; сравнение внутри одного снапшота; (2) «Client Fidel»: источник лида в `sources.repeat_client`, совпадение контакта не нужно. Так продавцы помечают повторных покупателей, чья первая покупка была до mefi (снапшот 28.09.2026: по контактам 0 повторных за 2026, при 195 из 195 клиентов с телефоном; Client Fidel 10 лидов, 3 клиента). Клиент с обоими признаками считается один раз с причиной «telefon/e-mail»: совпадение подтверждает покупку в mefi, источник это отметка продавца. В тексте m11 строка «Motiv» с числом по каждой причине для компании. Доля = повторные / клиенты месяца, 0 клиентов → «—». Разрез по шоуруму лида месяца (не прошлой покупки), строки как у `converted_count_by_showroom`, в тексте только шоурумы с клиентами. Лид WON без `converted_at` в расчёт не входит ни как клиент месяца, ни как прошлая покупка; их число по всему снапшоту идёт сноской (само расхождение уже алертит снапшот).
  Ограничения: общий телефон или e-mail в семье даёт ложное совпадение; клиент, оставивший другой номер и другой e-mail, не находится; клиенты без лида (заведённые в mefi руками) не участвуют; покупка до mefi (до 2026) видна только через источник Client Fidel, поэтому повторный клиент, которому продавец поставил другой источник, не находится, и в первые месяцы доля занижена. Источник Client Fidel ставит продавец: ошибочная отметка даёт ложного повторного, проверка по контакту её не отменяет.
- **m19, лист «Clienți luna»**: те же клиенты, что «din N» в m11, колонка «Zi conversie» = день `converted_at` по Бухаресту, «Revine» DA/NU, «Motiv» = «telefon/e-mail» или имя источника как в mefi («Client Fidel»), у не повторных пусто.

## Разбивка по источникам и кампаниям (m7, w6, shape `docs/shapes/2026-09-28-sources.md`)

Функции в `metrics/breakdown.py`, формулы не новые: те же флаги `count_flags` и `kpis_from`, что у компании, поэтому сумма строк равна `lead_counts` на том же окне по построению.

- **Ключи**: `source_name` (источник лида как в mefi) и `utm_campanie` (кастомное поле UTM_Campanie, читается из `raw` по `field_id` из `custom_fields.utm`; по краям срезаются пробел, таб, `\r`, `\n`, NBSP; пустая строка → нет значения). Значения не нормализуются.
- **`lead_breakdown`**: строки с LEADS ≥ порога, по убыванию LEADS, при равенстве по имени; ключи ниже порога сворачиваются в одну строку «Alte …» с суммой счётчиков и числом свёрнутых ключей; лиды без значения отдельной строкой («Fără sursă», `without_source_label` в status-mapping.yaml) и никогда не сворачиваются. PARTNERSHIP не входит, как в LEADS.
- **m7**: окно месяца (`month_window`), когорта на дату снапшота, как m2: итог m7 равен воронке компании m2. Столбцы Lead, Utile, Of., Cl., IRR, SCR; столбца визитов нет: визит определяется источником Showroom, в разрезе по источнику он тавтологичен. Кампании: строки с LEADS ≥ `min_campaign_leads`, лиды без кампании не выводятся строкой, вместо этого доля «N din M lead-uri au campanie» = лиды с кампанией / все лиды месяца.
- **w6**: окно недели (`weekly_window`), та же когорта, что w3: итог IRR равен IRR воронки недели (Showroom включён, поэтому «din N» не совпадает со счётом лидов w1). Рейтинг: ключи с LEADS ≥ порога, по IRR убыванию, затем по IRR_LEADS, затем по имени, первые `top_rows`; пустые источник и кампания в рейтинг не входят, но входят в итог. Цель по `targets.irr`, как в m5. Прошлая неделя по снапшоту её воскресенья, а не по текущему: IRELEVANT ставят с задержкой, по сегодняшнему снапшоту прошлая неделя выглядела бы хуже. Снапшота за воскресенье нет → первый успешный после него, но строго раньше снапшота отчёта (`first_snapshot_on_or_after(..., until=snapshot_date)`), с подписью «Săpt. trecută: după snapshotul din DD.MM (lipsește cel din DD.MM)»; свой снапшот отчёта не подставляется: в нём прошлая неделя дозрела, сравнение теряет смысл. Такого нет → «—» и подпись «Săpt. trecută: fără snapshot». IRR ключа на прошлой неделе без лидов → «—». Проценты w6 (строки, итог, прошлая неделя, цель) с одним знаком после запятой, как цель.
- **Подпись кампании в тексте** (m7, w6; только слой отчёта, данные не меняются): управляющие символы и переводы строк → пробел; длиннее `campaign_label_max_length` (params модуля, 40) → обрезка с «…»; 7+ цифр подряд или «@» вместе с точкой → `hidden_campaign_label` («campanie ascunsă»), контакт клиента в группу не выводится (инвариант 7).
- Источник лида в mefi можно поменять: прошлые периоды считаются по источнику на дату снапшота, как шоурумы в m2.

## Касания консультантов (w14, shape `docs/shapes/2026-09-29-touches.md`)

Функции в `metrics/touches.py`. Revenire 1/2/3 это первое, второе, третье касание менеджера, не визит (ADR-007).

- **Касание**: лид в снапшоте S_i стоит в статусе из `ACTIVE_FOLLOWUP.statuses`, а в предыдущем успешном снапшоте S_{i−1} стоял в другом статусе, либо отсутствовал и создан после конца окна дня S_{i−1} (новый лид сразу в Revenire N). Лид, которого не было в S_{i−1}, но созданный раньше, не касание. Приписывается `assigned_to` в S_i.
- **Уровень** = позиция статуса в `ACTIVE_FOLLOWUP.statuses` (1, 2, 3); новый статус в конце списка станет следующим уровнем без правки кода. Пропуск уровня (IN PROCES → Revenire 2, Revenire 1 → Revenire 3) и переход вниз это одно касание на уровне, куда лид пришёл.
- **День касания** = ежедневное окно (`daily_window_days`), содержащее `status_changed_at` в S_i, при null `created_at`. День вне пары (не позже дня S_{i−1} или позже дня S_i) прижимается ко дню S_i. Разница снапшотов решает, было ли касание, `status_changed_at` только датирует.
- **Период** = цепочка пар соседних success-снапшотов: последний success раньше первого дня периода плюс все success внутри (`touch_snapshot_dates`), касания фильтруются по дню касания. Превью (до 19:00) в цепочку не входят. Покрытые дни без своего снапшота перечисляются сноской; снапшота до периода нет: дни до первого снапшота периода включительно не покрыты, сноска «Atingeri numărate de la DD.MM»; ни один день не покрыт: «fără date».
- **Группы** как в d3: консультант по `assigned_to_id`, не взятые («Nepreluate») первыми, затем по числу касаний и имени; активный консультант (`active: true`) без касаний строкой «0». Ссылок на лиды нет.
- **Только недельный вариант**: дневное число меряет, когда консультант обновил CRM, а не когда звонил (массовые правки статусов).

Ограничения:
- касание, после которого лид в тот же день ушёл дальше (Revenire 1 → Clienți, Revenire 1 → Revenire 2), не видно: снапшот раз в день, `status_changed_at` хранит только последнюю смену (инвариант 3); два касания за день это одно;
- Revenire N → другой статус → тот же Revenire N за день не видно;
- касание это запись статуса в mefi, а не звонок: звонков (источник C) нет; массовая правка статусов попадает в день правки;
- при пропуске снапшота теряются касания дня, лид которых ушёл дальше до следующего снапшота;
- пропуск уровня считается одним касанием;
- лид, переназначенный после касания, отдаёт касание ответственному в S_i; лид, удалённый в mefi до S_i, касания не даёт;
- лид, удалённый и восстановленный между соседними снапшотами, касания не даёт;
- поздний снапшот воскресенья (после 19:00) видит касания уже следующего окна; они прижимаются к воскресенью и попадают в неделю W, а не W+1. Принято: сдвиг на одно касание на границе недели дешевле, чем отдельная логика для последней пары;
- смена статуса с `status_changed_at` = null датируется `created_at` и прижимается ко дню S_i; число прижатых строк пишется в лог warning.

## Режим вопросов (shape `docs/shapes/2026-09-27-chat.md`)

- **Периоды чата** (`metrics/chat_periods.py`): период = ежедневные окна его дней подряд. `azi`, `ieri` = одно окно d1; `saptamana_curenta` = понедельник..сегодня, `saptamana_trecuta` = `weekly_window` прошлого воскресенья; `luna_curenta` = первое число..сегодня, `luna_trecuta` = `month_window`; `ultimele_30_zile` = 30 окон по сегодня.
- **Кадр**: закрытые периоды (`ieri`, `saptamana_trecuta`, `luna_trecuta`) по снапшоту своего последнего дня, по которому ушёл отчёт; остальные по последнему успешному снапшоту. Снапшота за последний день закрытого периода нет → первый успешный снапшот после него, подпись «Date din snapshotul din 25.09.2026 (nu există snapshot pentru 31.08.2026)»; когорта в нём дозревшая, а потери периода могут недосчитать лиды, сменившие статус после конца периода. Нет и более позднего → «нет данных». Текущий период, снапшот которого раньше последнего дня, считается на дату снапшота с подписью «Date din snapshotul din …».
- **Конкретные день и месяц** (shape `docs/shapes/2026-09-27-chat-dates.md`): `{"day": "2026-09-25"}` = `daily_window` этого дня, `{"year": 2026, "month": 8}` = `month_window`. Кадр по правилу закрытых периодов. Сегодняшний день читается как `azi`, текущий месяц как `luna_curenta`. Дата позже сегодняшней или раньше первого успешного снапшота минус 12 месяцев: ошибка инструмента. Подпись «Perioada: 25.09.2026», «Perioada: august 2026». Сегодняшняя дата по Бухаресту в системном промпте, год у даты без года выбирает модель: самый недавний, не в будущем.
- **Уточняющие вопросы** (shape `docs/shapes/2026-09-27-chat-followups.md`): контекст = один предыдущий обмен из `chat_questions` со статусом `answered`: вопрос, на ответ которого сделан reply (без ограничения по времени и пользователю), иначе последний вопрос того же пользователя в том же чате моложе `chat.context_minutes` (10) по часам Postgres. Модель видит только прошлый вопрос и успешные вызовы с аргументами, блоком перед текущим вопросом; ответ и результаты не передаются, страж сверяет числа только с текущими вызовами. В лог `context_question_id` и `reply_message_id`.
- **Контракты по шоуруму** (`converted_count_by_showroom`): лиды с `converted_at` в окне, разрез по шоуруму лида, как у `converted_count`; шоурум вне списка и лид без шоурума получают свою строку. Сумма по шоурумам = `converted_count`. d6 и w8 его пока не используют.
