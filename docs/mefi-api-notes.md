## Подтверждено

- **Search отдаёт полные карточки вместе с `custom_fields`.** Во всех 16 полученных лидах есть 12 кастомных полей в одинаковом порядке.
- **Решение: `GET /leads/{id}` на каждый лид не нужен.** От search ответ отличается только ключом `company` (замер 25.08, только для `client_type: company`), а его мы не используем. Брифовый вопрос §11.7 закрыт.
- Даты: ISO 8601 UTC с суффиксом `Z`, точность до секунды (`2026-09-24T10:04:38Z`).
- `date_from = date_to` возвращает лиды этого дня, значит `date_to` включительная.
- `estimated_value = null` у 16 из 16 лидов. Деньги берём только из источника B.
- Шоурум: `custom_fields[field_id=14]`, `name: "Showroom"`, `type: select`, значения `București` / `Brașov` / `Cluj`. `location.city` содержит город клиента (`Bacau`, `Pascani`) и к шоуруму отношения не имеет.
- `Ofertat`: `field_id=20`, `type: select`, значения точно `"✅DA"` и `"❌NU"` (эмодзи без пробела), в выборке оба.
- `Data revenire`: `field_id=5`, `type: date_picker`, строка `YYYY-MM-DD` без времени и зоны, иначе `null`.
- Заметки недоступны: скоуп `leads:read:notes` у mefi «coming soon», endpoint'а нет.

## Поведение временных полей (важно для speed-to-lead)

По 13 лидам от 22.09:

- **`last_contact_at` при создании равен `created_at`** (у 6 из 13 точное совпадение, до секунды). Касания после этого **перезаписывают** значение: это последнее касание, а не первое. Пример: лид 2994 создан 22.09 07:03Z, `last_contact_at` 23.09 07:08Z, статус не менялся.
- **`status_changed_at = null`, если статус задан при создании.** Пример: лид 3028 создан сразу в `Ofertat`, 2997/2998 сразу в `IRELEVANT`. Значит, `status_changed_at` не отражает «первое движение».
- Статус иногда меняют через секунды после создания (3007: +8 с). Это ввод данных продавцом, а не касание клиента.
- Лиды из `Telefon`, `WhatsApp`, `Showroom` создаёт сам продавец (`created_by = assigned_to`) уже после разговора. Для них speed-to-lead по определению ≈ 0.

Вывод: `min(status_changed_at, last_contact_at)` из одного снапшота первое касание не даёт.

## Speed-to-lead — основа для ADR-003

Формула брифа (`first_touch = min(первая заметка, первое изменение статуса, last_contact_at)`) недействительна. Заметки недоступны (`leads:read:notes` не выпущен), а поля времени ведут себя, как описано выше. В `docs/kpi-definitions.md` метрика помечена как недействительная до ADR-003. В MVP w5 выключен.

### Почему не работает `min(status_changed_at, last_contact_at)` по одному снапшоту

- `last_contact_at` при создании равен `created_at`, так что у нетронутого лида speed-to-lead получился бы 0.
- `last_contact_at` перезаписывается последним касанием, поэтому по одному снапшоту видно последнее касание, а не первое.
- `status_changed_at` = null, если статус задан при создании, и иногда меняется через секунды после создания: это ввод данных, а не касание.
- Лиды `Telefon` / `WhatsApp` / `Showroom` продавец заводит после разговора, для них метрика ≈ 0 по определению.

### Предложенная формула (черновик для ADR-003)

`speed_to_lead = first_touch_at − created_at` в рабочих часах. Отчёт показывает медиану и долю > 4 рабочих часов.

- `first_touch_at` — самое раннее значение `min(status_changed_at, last_contact_at)` по снапшотам, где это значение позже `created_at` больше чем на порог ввода (конфиг).
- Считается только по источникам, где лид приходит без продавца (конфиг: `Site`, `Mail`, `Meta ADS`).
- Лид, у которого касания нет, в медиану не входит и считается отдельно как «без касания».

### Точность и что решить в ADR-003

- Точность зависит от частоты снапшотов. Если между двумя снапшотами было несколько касаний, получаем верхнюю оценку: промежуточное касание затёрто.
- При ежедневном снапшоте порог «4 рабочих часа» не измерить. Нужен частый опрос изменённых лидов, например раз в 15–30 минут `POST /leads/search` с `date_field=last_contact_at`, `date_from=сегодня`; это 1–2 запроса за цикл. Схема хранения должна сохранять каждое наблюдение касания, а не только последний снапшот.
- Значение порога ввода. Наблюдали изменение статуса через 8 с после создания, 60 с — кандидат, проверить на данных.
- Перечень источников «без продавца» подтвердить с клиентом.

## Наблюдения о качестве данных

Выборка — 13 лидов, созданных 22.09.2026 (вызов 3). Это наблюдения, а не проверенные правила mefi: подтвердить на первых снапшотах.

- **`Data revenire` у 7 из 13 лидов равна дню создания** (`2026-09-22`). Форма по умолчанию дату не подставляет (см. проверку интерфейса ниже), это выбор продавца, но `d3 «просроченные revenire»` (он в MVP) на следующий день поднимет почти все свежие лиды. До включения d3 нужно правило отсечения, например не считать `Data revenire = дата создания (Europe/Bucharest)` назначенным follow-up.
- **`last_contact_at` при создании равен `created_at`** (6 из 13 совпадают до секунды, у всех трёх лидов вызова 1 тоже). Значит, `last_contact_at == created_at` означает «касаний не было», а не касание в момент создания. Любая метрика «лиды без касания» (`d2`) должна проверять именно это равенство, а не `last_contact_at IS NULL`.
- **Проверено в интерфейсе mefi 24.09.2026:**
  - `Data revenire` в форме создания по умолчанию пустая; совпадение с днём создания это выбор продавца.
  - Флажок «Contactat astăzi» включён по умолчанию, поэтому `last_contact_at` = `created_at`.
  - `Desemnat` по умолчанию «Sofa Marketing» (id 7): лид на нём означает «никто не взял».
  - `Clienți` нет в форме создания, но выбирается на карточке лида после подписания контракта; `converted_at` ставит mefi при этой смене.
  - В том же меню карточки есть `Pierduți` и `Eliminați`, они задают lifecycle `lost`/`junk`; продавцы выбирают статус потери, а не их, поэтому потерянные лиды остаются `active`.
  - Полный список статусов: 17 из `enums.md` плюс `SPAM` и `BIFE 2026`.
- **Статус может меняться через секунды после создания** (лид 3007: `status_changed_at` через 8 с после `created_at`). Это ввод данных продавцом, а не движение по воронке. Для метрик, чувствительных ко времени, нужен порог ввода (конфиг).

## Лимиты и правило паузы

Заголовки из всех 5 ответов:

```
x-ratelimit-limit: 600
x-ratelimit-remaining: 97..99
x-ratelimit-reset: 1790247720   (= 11:02:00 UTC, граница минуты)
```

- Заголовки показывают **только лимит токена** (600/мин; `remaining` около 99 — это корзина burst 100/10 с). IP-лимит 10 запросов / 10 с в заголовках не виден, поэтому темп по `remaining` подбирать нельзя.
- Реальный потолок **~1 req/s по IP**: замер 25.08.2026, 429 на 11-м запросе при интервале 0.35 с, 21 запрос подряд без 429 при 1.2 с. Сегодня 429 не воспроизводили, лимит вызовов сессии — 6. Сегодняшние 5 вызовов с паузой 1.2 с прошли без 429, это согласуется с замером.
- **Правило:** между любыми запросами к mefi с нашего хоста пауза ≥ 1.2 с, глобально на процесс, а не на задачу. На 429 ждём `Retry-After` и повторяем; одиночный 429 прогон не валит, но уходит в служебный бот.

## Размер снапшота

2987 лидов на 24.09.2026 → 30 страниц по 100 → ~36 с при паузе 1.2 с. С ростом ~300 лидов в месяц через год это ~66 страниц и ~80 с. Полный ежедневный снапшот укладывается с большим запасом, инкрементальный sync для MVP не нужен.
