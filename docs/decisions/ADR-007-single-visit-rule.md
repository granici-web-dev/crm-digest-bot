# ADR-007 · Одно правило визита во всех расчётах

Статус: **accepted** (29.09.2026). Shape: `docs/shapes/2026-09-29-visit-rule.md`, раздел «Согласовано». Формулы: `docs/kpi-definitions.md`, «Признаки лида», «Визит».

## Контекст

ADR-006 ввёл в d1 правило revenire: Showroom-лид, чей контакт встречался у лида, созданного раньше начала окна, это не визит, а Alte. w2, KPI (SHOWROOM_VISITS, SC), w8 и чат считали визитом любой лид с источником Showroom, включая партнёрские. За неделю 39 директор видел в w2 28 визитов, а в w6 «din 27».

## Решение

- Визит это свойство лида, а не отчётного периода: `digest.metrics.visits.showroom_visit_flags` считает один раз в `prepare_lead_frame` три колонки: `is_showroom_source` (источник из `sources.showroom_visit`, любой приход), `is_showroom_revenire` (не PARTNERSHIP, контакт совпал с лидом, созданным раньше начала **собственного** ежедневного окна лида), `is_showroom_visit` (не PARTNERSHIP и не revenire).
- Граница revenire это начало ежедневного окна, содержащего `created_at` лида. Для лида из окна d1 это начало окна d1, поэтому d1 не меняется. Неделя (w2, w6, w8), месяц и периоды чата состоят из ежедневных окон и на одном снапшоте равны сумме дней d1 по построению; с уже отправленными d1 сумма может разойтись только из-за разных снапшотов (переход в PARTNERSHIP, удалённый ранний лид), не из-за правила визита.
- Все потребители читают колонки. w2, лист «Vizite» w12, визиты w8, SHOWROOM_VISITS и SC (m2, m4, m5, m7, w3, w6, SPI, чат) берут `is_showroom_visit`. w1 («FARA Showroom») и d2 («приход сам по себе касание») берут `is_showroom_source`: смысл у них прежний.
- SC: revenire не входит ни в числитель, ни в знаменатель; конверсия визита это только сам лид визита, числитель ⊂ знаменатель. Атрибуция продажи по контакту к первому визиту это отдельный ADR, когда появятся случаи.
- w2 показывает строку `Reveniri: N` только при N > 0 (пересмотрено 29.09.2026, см. «Повторный приход»): ноль означает отсутствие данных, а не отсутствие возвратов.

## Факты (снапшот 28.09.2026)

mefi дубли разрешает (4 лида с `is_duplicate`), телефон делят 34 лида из 3056, пар Showroom–Showroom с общим контактом нет, `Data revenire` заполнена у 1441 лида. Вывод: повторный приход не заводится новым лидом, как предполагал ADR-006 (уточнено ниже: в mefi он не фиксируется вовсе); revenire по контакту ожидаемо ≈ 0. Правило по ADR-006 оставляем: оно дёшево и ловит редкий случай повторного лида. Метрика повторного визита по изменению существующего лида это отдельный shape после ответа владельца.

## Повторный приход (уточнение пользователя 29.09.2026)

Повторный приход в шоурум в mefi не фиксируется. Статусы Revenire 1/2/3 это первое, второе, третье касание менеджера с клиентом, а не визит. Строка продавцов «Leads Alte/Showroom (revenire)» это повторный приход в шоурум (например, подписать договор). Следствия:

- revenire по контакту остаётся (ловит повторный лид), но его ноль не значит «никто не вернулся»;
- w2: строка `Reveniri: N` только при N > 0;
- d1: под блоком одна сноска «Revenirile în showroom nu sunt înregistrate în CRM și nu sunt incluse.»;
- метрика касаний менеджеров (переходы в Revenire N между снапшотами) это кандидат, отдельный shape; способ фиксировать приход это вопрос В1 владельцу (`docs/owner-questions.md`).

## Последствия

- Эталон 2026-05 не меняется: в workbook нет повторных контактов, оракул `scripts/build_etalon.py` считает revenire сам, независимо от `metrics/` (попарное сравнение контактов с границей 19:00 начала окна лида), на workbook revenire 0. Правило revenire покрыто unit-тестами `tests/unit/test_metrics_visits.py`, включая 18:59 → 19:01 с тем же телефоном = revenire (вопрос П4 владельцу).
- Неделя 39 по снапшоту 28.09: w2 28 → 27 (1 партнёр, 0 revenire). SC за сентябрь не меняется.
- Снапшоты до миграции 0005 без ключей контакта: там revenire невидим, визит = Showroom без партнёров.
- Удалённый в mefi ранний лид превращает revenire в визит задним числом (сравнение внутри снапшота), как в ADR-006.
